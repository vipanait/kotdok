# Обновление уязвимых зависимостей — цикл проверки 20260906-111013Z

Закрывает пункт 1.9 открытых вопросов. База: коммит `d07e473`, ветка `security/dependency-updates`, отведена от `main`.

Окружение: macOS 26.6.2 arm64, Node v25.2.1, npm workspaces, локальный стенд Supabase CLI 2.115.0.

Изменение содержит **только безопасность**: продуктового кода не тронуто ни строки, изменены три файла — `package.json`, `apps/web/package.json`, `package-lock.json`.

## Почему нельзя было обойтись `npm audit fix`

`npm audit fix` завершается ошибкой `ERESOLVE`. Единственный путь, который он находит для куста `@expo/*`, — откат `expo` с 57 на 40/46, что противоречит закреплённой связке Expo SDK 57 + React Native 0.86.3 (решение 1 отчёта этапа 0.1). Поэтому обновление сделано адресно.

Второе препятствие: `overrides` в корневом `package.json` применяются только при полном разрешении графа. После обычного `npm install` версии не менялись — то же наблюдение зафиксировано в записи прогона этапа 0.1. Пакеты переразрешены точечно через `npm update <имена>`, чтобы не тащить полную пересборку lockfile, запрещённую приёмкой 0.1/02.

### 3. Удалён `resend`

`resend` был объявлен в зависимостях веба, но **не импортируется нигде**: поиск по всему репозиторию без учёта регистра даёт только саму строку в `package.json`, упоминания в отчётах и имя `RESEND_API_KEY` в списке запрещённых строк проверки бандла. Переменной `RESEND_API_KEY` нет ни в одном окружении Vercel.

Это мёртвая зависимость и единственный источник трёх moderate: `resend` → `svix@1.88.0` → `uuid@10.0.0` (отсутствие проверки границ буфера в v3/v5/v6). Удаление убирает их вместе с `svix`, `uuid@10`, `standardwebhooks`, `postal-mime`, `@stablelib/base64` и `fast-sha256` — семь пакетов из графа production.

Если транзакционная почта понадобится, зависимость возвращается текущей версией. То, что typecheck, все тесты и production-сборка проходят без неё, — доказательство, что её никто не использовал.

## Что осталось и почему не чинится

Все 13 оставшихся — один связный куст инструментария Expo: `@expo/cli`, `@expo/config`, `@expo/config-plugins`, `@expo/inline-modules`, `@expo/local-build-cache-provider`, `@expo/metro-config`, `@expo/prebuild-config`, `expo`, `expo-router`, `xcode`, `uuid@7.0.3`, `query-string@7.1.3`, `decode-uri-component`.

Три причины оставить как есть:

1. **Починить нельзя.** Единственное, что предлагает npm, — `expo@46.0.21` и `expo-router@5.1.11`, то есть откат на несколько лет назад с потерей SDK 57. Диапазоны самих пакетов не допускают исправленных версий `uuid` и `query-string`, а подмена через `overrides` меняет мажорную версию `uuid` (7 → 11) под кодом, который её не ожидает.
2. **До пользователя не доезжает.** Это код `expo prebuild` и CLI, работающий на машине разработчика и на сборочной машине. Проверка `verify:bundle` подтверждает состав бандлов отдельно.
3. **Сами уязвимости — DoS на разборе входных данных** (`decode-uri-component` на битой percent-кодировке, `uuid` при явной передаче буфера в v3/v5/v6). Во всех случаях вход — собственные конфиги проекта, а не чужие данные.

Пересматривать при выходе следующего Expo SDK.

## Побочная находка: preview-деплои Vercel ломаются на Next 16.3

Первые два preview-деплоя ветки завершились ошибкой. Сборка при этом проходила полностью — все маршруты отрисованы, `Build Completed in /vercel/output [47s]`. Падал следующий шаг, выкладка:

```
Cannot patch preview comments when immutable static file upload is enabled.
Upgrade to next@v16.3.0-canary.32 or newer to resolve this.
```

Совет в сообщении противоречит сам себе: 16.3.4 новее, чем 16.3.0-canary.32. Проверка версии на стороне Vercel устарела. Версию платформа при этом определяет верно — в логе есть строка `Detected Next.js version: 16.3.4`, так что дело не в монорепозитории и не в нашем `vercel.json`.

Суть в том, что Next 16.3 выкладывает статические файлы неизменяемыми, а панель Vercel вписывает в них скрипт комментариев. Патчить нечего, и выкладка падает.

Диагноз проверен экспериментом: разовый деплой с `--env VERCEL_PREVIEW_FEEDBACK_ENABLED=0` собрался и открылся (`kotdok-i4yoiu3sn`, Ready, 59 с). После этого переменная `VERCEL_PREVIEW_FEEDBACK_ENABLED=0` задана в окружении **Preview** — по решению владельца. Production не затронут: там нет preview-комментариев, патчить нечего и без переменной. Первый же git-деплой ветки после этого прошёл (`kotdok-p44z25ukk`, Ready).

Цена решения — на preview-деплоях больше нет панели Vercel с комментариями. Снимается удалением переменной, когда платформа починит проверку версии.

## Чего эта запись не подтверждает

- **Ручной осмотр preview.** Preview закрыт аутентификацией Vercel (`ssoProtection: all_except_custom_domains`), секрета обхода в проекте нет, поэтому из командной строки все маршруты отвечают `302` на `vercel.com/sso-api`. Осмотр страниц в браузере — за владельцем.
- **Прогон в CI.** Проверяется на PR.
- **Нативные сборки Expo.** Экспорт JS не подтверждает сборку под iOS и Android — это ограничение сохраняется с этапа 0.1 и упирается в пункт 1.13.
