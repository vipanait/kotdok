## Уязвимость: прямая запись в БД пользовательским токеном

Найдена при работе над пунктом 1/03, подтверждена воспроизведением, исправлена и применена к production.

### Как обнаружена

Добавляя `profiles.status`, я запустил тест «пользовательский токен не может сменить состояние аккаунта». Тест прошёл — но по неверной причине: клиент получал `42501 permission denied for table profiles` на **любой** запрос, включая чтение. Проверка вхолостую не считается проверкой, поэтому я сверил гранты локального стенда с рабочей базой.

Расхождение: в рабочей базе роли `anon` и `authenticated` имеют `DELETE, INSERT, REFERENCES, SELECT, TRIGGER, TRUNCATE, UPDATE` на все 12 таблиц `public` — это платформенные default privileges Supabase. Локальный стенд их не имел, потому что базовая миграция создавала таблицы без них. Стенд был **защищённее** production, из-за чего проблема была невидима.

### Что именно не так

Политики на `profiles`, `pets`, `symptom_checks` и `credit_transactions` были написаны как `for all using (auth.uid() = ...)` без `with check`. Для `UPDATE` выражение `USING` отбирает строки, а при отсутствии `WITH CHECK` оно же служит проверкой результата. В сочетании с грантом `UPDATE` это означает: вошедший пользователь, имея только публичный anon-ключ из браузера, пишет в свои строки напрямую через PostgREST.

### Воспроизведение

Гранты добавлены в базовую миграцию, чтобы стенд повторял платформенное поведение; `supabase db reset`, затем вход фикстурой `owner-a@fixture.local` через `signInWithPassword` с anon-ключом:

```
select: {"data":[{"id":"a1ee...","credits":5}],"error":null,"status":200}
update: {"data":[{"id":"a1ee...","credits":9999,...}],"error":null,"status":200}
credits after: 9999
```

Обычный пользователь выставил себе баланс 9999 одним запросом. Тем же путём ставится `role = 'admin'`. Практические последствия: неограниченные бесплатные AI-проверки и самоназначение администратором. На рабочей базе эксплуатация не проводилась и не требовалась: гранты и определения политик там идентичны.

### Исправление

Миграция `20260906000000_account_status_and_write_lockdown.sql`:

- отзывает `insert, update, delete, truncate, references, trigger` у `anon` и `authenticated` на всех таблицах `public`;
- меняет default privileges, чтобы новая таблица не открыла дыру заново;
- сужает четыре политики до `for select`;
- удаляет политику вставки `user_feedback`: маршрут обратной связи пишет через service role, клиенту привилегия не нужна.

Чтения сохранены намеренно: страницы `/checks` и `/check/[id]` читают `symptom_checks` через сессию пользователя, `require-admin-user` читает `profiles`. Проверено, что ни одна запись в приложении не выполняется пользовательским токеном — все записи идут через service role.

После миграции на стенде:

```
select: 200, данные возвращаются
update: 403 permission denied for table profiles
credits after: 5
```
