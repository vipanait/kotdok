## История

| Проверка | Результат |
| --- | --- |
| Только свои активные записи | владелец A видит две, владелец B — одну из двух |
| Мягко удалённая запись | не возвращается ни в списке, ни по прямому ID |
| **Пагинация при одинаковых датах** | у владельца A обе проверки имеют один `created_at` (подтверждено запросом: `count(distinct created_at) = 1`). Обход постранично по одной записи возвращает обе, каждую ровно один раз, без повторов |
| Фильтр по питомцу | возвращается только проверка этого питомца |
| Размер страницы больше максимума | 400 `bad_request`, а не молчаливое урезание |
| Размер страницы 0 и дробный | 400 |
| Испорченный курсор | 400 |
| Чужая запись по прямому ID | 404 |
| Формат дат | каждая запись оканчивается на `Z` |

Курсор — пара `(created_at, id)` в base64url. Пагинация только по времени теряла бы или повторяла записи именно на этой фикстуре; поэтому обе половины едут вместе, и порядок становится полным.

## Баланс

Значение из `/api/v1/me` совпадает с колонкой `profiles.credits`, которую рендерит кабинет сайта, и с ожидаемым значением фикстуры. После списания кредита через `apply_symptom_check_usage` API отдаёт новое значение, и оно равно сумме `delta` по `credit_ledger` — то есть баланс и журнал движутся вместе.

Записать баланс через продуктовый маршрут нельзя: тело с полем `credits` отклоняется строгой схемой (400), значение в БД не меняется.

## Найденное при реализации

**`.single()` превращал «не твоё» в 500.** `updatePet` и `softDeletePetAndChecks` использовали `.single()`, который сообщает об отсутствии подходящей строки ошибкой, а не пустым результатом. Поэтому попытка изменить чужого питомца отвечала 500 вместо 404 — и на **старом веб-маршруте** тоже, где это никогда не проявлялось в тестах, потому что сервис там был замокан. Обе функции переведены на `maybeSingle()`.

**Даты без часового пояса.** `pets.created_at` и `symptom_checks.created_at` — `timestamp without time zone`; Supabase отдаёт их как `2026-05-01T10:00:00`, без зоны. Контракт такие значения отклоняет, а клиент прочитал бы их в своём локальном времени. Добавлен общий помощник `toUtcIso`, который явно проставляет UTC — ту зону, в которой они и записаны сервером. Отдельный тест фиксирует, что сырое значение контракт действительно не принимает.
