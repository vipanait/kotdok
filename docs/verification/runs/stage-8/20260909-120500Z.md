# Прогон 8/07: что приходит слишком поздно

- **Дата:** 9 сентября 2026, 19:45–20:05 (UTC+8)
- **Код:** ветка `server/stage-8-late-callbacks`
- **Окружение:** локальный стенд Supabase, Postgres 17, интеграционные тесты
  против настоящей БД

## Что оказалось не защищено

Ни одна из шести функций, которые пишут по чужому сигналу — `apply_symptom_check_usage`,
`refund_symptom_check_usage`, `resolve_extra_check_request`, `apply_transaction_success`,
`apply_refund`, `create_extra_check_request` — **не смотрела на состояние аккаунта**.
Проверено запросом к их телам, а не на глаз.

Существующий помощник `current_account_is_active()` тут не помогает: он читает
`auth.uid()`, а поздние вызовы приходят через сервисную роль, где `auth.uid()`
пуст. По той же причине бесполезны и политики RLS — сервисная роль их не
соблюдает.

**Опасное окно — статус `deleting`, а не «удалён».** После удаления пользователя
из Auth большую часть таких записей отвергают внешние ключи. А пока статус
`deleting`, строки все на месте, очистка может идти прямо сейчас, и поздняя
вставка ложится в данные, которые стирают, и переживает их.

## Решение: заслон на таблицах, а не в функциях

Дописать проверку в шесть функций значит однажды забыть её в седьмой — а
критерий 8/07 как раз про вызовы, о которых никто не помнит: они приходят позже,
из другого места, часто через сервисную роль. Триггер стоит на пути у любого
пути по построению, включая те, что ещё не написаны.

Восемь таблиц: `pets`, `symptom_checks`, `check_jobs`, `credit_ledger`,
`credit_transactions`, `transactions`, `extra_check_requests`, `user_feedback` —
плюс отдельный триггер на `profiles`, который срабатывает **только когда
меняется `credits`**. Иначе он запретил бы то единственное обновление, с
которого всё начинается: перевод аккаунта в `deleting`.

**Удаления разрешены намеренно.** Сама очистка состоит из них, и заслон, который
бы их блокировал, мешал бы удалению, ради которого он и поставлен.

## Приёмка

| Поздний вызов | Результат |
| --- | --- |
| Ответ анализа записывает проверку | Отказ |
| Он же записывает свою задачу | Отказ |
| Списание кредита за эту проверку | Отказ |
| Одобрение из Telegram заводит запрос | Отказ |
| Платёжный webhook открывает транзакцию | Отказ |
| Он же двигает баланс | Отказ |
| Он же пишет строку в журнал баланса | Отказ |
| Возврат кредита | Отказ |
| Питомец добавляется | Отказ |
| Питомец помечается удалённым (повтор удаления) | Отказ |
| Полное удаление питомца | **Разрешено** — из этого состоит очистка |
| Данные второго владельца | Не затронуты: он пишет питомца и меняет баланс как обычно |
| Аккаунт, которого уже нет | Отказ с внятной причиной, а не нарушение внешнего ключа |

Тринадцать тестов. Заслон при этом **не сломал ни одного существующего
поведения**: до его добавления сюита давала 128 из 128, после — 127 и одно
падение, и то был закреплённый список функций схемы, куда просто не внесли две
новые.

## Ошибка в самом прогоне

Тест «полное удаление разрешено» сперва упал на внешнем ключе
`symptom_checks_cat_id_fkey`: я удалял питомцев, не удалив сначала проверки.
Это не дефект заслона, а моё несоблюдение порядка, который выведен в карте
данных — журнал баланса держит проверки, проверки держат питомцев. Тест
исправлен и теперь идёт по карте, то есть заодно её и проверяет.

## Чего этот заслон не делает

Он запрещает записи, но **не отменяет уже начатую работу**. Анализ, запущенный
до запроса на удаление, честно доработает и получит отказ при попытке записать
результат — то есть кредит за него уже списан, а результата не будет. Это
правильный компромисс для 8/07 (лучше потерять результат, чем воскресить
аккаунт), но остановкой задач занимается 8/05, и там это надо будет сделать
аккуратнее: сперва остановить, потом удалять.
