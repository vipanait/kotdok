# Прогон 8/03, 8/04, 8/06 и механизма 5/08

- **Дата:** 9 сентября 2026, 18:55–19:25 (UTC+8)
- **Код:** ветка `server/stage-8-deletion-request`, коммиты `b101fa9` и `d05dce9`
- **Окружение:** локальный стенд Supabase, Postgres 17, интеграционные тесты
  против настоящей БД и настоящего GoTrue

## Почему пришлось начать с этапа 5

Формулировка 8/03 начинается словами «После серверной проверки свежего
подтверждения личности **из этапа 5**». Такой проверки не было: контракт
`AccountDeletionRequestSchema` требует `reauth_token`, а выдавать и проверять
его было некому. Поэтому сначала построен механизм 5/08, затем на нём — 8/03.

## Свежесть аутентификации: сперва замер, потом код

Механизм держится на claim `amr` в токене доступа, который записывает, когда
человек **действительно** аутентифицировался. Прежде чем на это опираться, я
проверил поведение на staging:

| | `amr[0].timestamp` | `iat` |
| --- | --- | --- |
| Вход по паролю | 1788951480 | 1788951480 |
| Обновление токена через 3 секунды | **1788951480** | 1788951483 |

`iat` сдвинулся, `amr` — нет. Это ровно то свойство, которого требует приёмка
5/08 («обновление access token и клиентский флаг проверку не проходят»), и
обеспечивает его устройство токена, а не наши соглашения. Работает одинаково
для пароля, Google и Яндекса — каждый способ пишет свою запись; заработает и
для Apple, когда он появится.

Токен читается **уже проверенным**: `withApiAuth` перед этим отдал его Supabase
и получил подтверждение. Разбор полезной нагрузки после этого — чтение claim из
проверенного другим токена, а не доверие непроверенному; в коде это оговорено
отдельно, потому что перепутать легко.

## Что построено

| Объект | Назначение |
| --- | --- |
| `reauth_proofs`, `consume_reauth_proof` | Одноразовое доказательство: привязано к паре «пользователь + операция», живёт пять минут, хранится только хеш. Проверка и трата — один `update`, поэтому два запроса подряд не могут оба получить «да» |
| `deletion_jobs`, `request_account_deletion` | Пометка аккаунта и задача очистки в одной транзакции |
| `retain_until`, `purge_expired_deletion_jobs`, `complete_deletion_job` | Срок хранения самой записи |
| `POST /v1/auth/reauth`, `POST /v1/account-deletion` | Маршруты; оба описаны в OpenAPI |
| `reauth_required` | Отдельный код ошибки: «подтвердите личность» — не то же самое, что «войдите заново», и следующий шаг клиента другой |

Задача **намеренно без внешнего ключа** на `auth.users`: 8/04 требует, чтобы она
пережила удаление пользователя. Каскад стёр бы запись о работе в момент, когда
работа почти закончена, а `restrict` — наоборот, помешал бы самому удалению.

## Приёмка

| Требование | Результат |
| --- | --- |
| Параллельные запросы создают одну задачу и одно состояние `deleting` | PASS — десять одновременных запросов, одна задача. Решает уникальный ключ по `user_id`, остальные проходят `on conflict do nothing` |
| Сбой не оставляет половинного состояния | PASS — для несуществующего аккаунта функция возвращает false и не оставляет ни строки |
| Обычные пути доступа отклоняются сразу | PASS — `withApiAuth` отвергает аккаунт со статусом `deleting`, то есть повторный запрос до этого обработчика не доходит вовсе |
| Проof привязан к пользователю и операции, одноразовый, с TTL | PASS — пять тестов: повтор, чужой владелец, истечение, несуществующий, хранение только хеша |
| Задача и квитанция переживают удаление Auth | PASS |
| В задаче нет лишних полей профиля | PASS — только хеш квитанции, статус, прогресс и время; ни адреса, ни имени |
| По истечении TTL чистятся | PASS механизма, **оговорка по значению**: срок должен покрывать опубликованный срок удаления, а тот блокирован вопросом 1.8. `retain_until` остаётся пустым, и пустое означает «никто не решил», а не «истекло» |
| Незавершённая работа не сметается | PASS — сколько бы ей ни было лет: потерять эту строку значит потерять само удаление |
| Старые токены не открывают данные после удаления | PASS — токен, взятый до удаления, не отдаёт ни `pets`, ни `symptom_checks`, ни `profiles`, ни `credit_ledger`. Проверено **в обход наших маршрутов**, прямо у PostgREST, потому что JWT остаётся подписанным до истечения и не становится отозванным сам собой |
| Данные второго пользователя не открываются | PASS |

## Дефект в уже слитом коде, найденный этим прогоном

**У `archive_account_financials` не было права на выполнение для `service_role`.**
Миграция `20260908150000` заканчивалась `revoke all ... from public, anon,
authenticated` — и на этом. `service_role` наследует право выполнения от
`public`, так что отзыв запер и доверенный сервер: каждый вызов через PostgREST
возвращал ошибку, которую вызывающий не проверял, а финансовые строки
оставались на месте.

Почему не заметили раньше: тест этой функции зовёт её по прямому соединению от
владельца базы, где права вообще не участвуют. Здешний тест ходит через
сервисный клиент — так же, как будет ходить задача очистки, — и упал на внешнем
ключе, который архив должен был расчистить.

Исправлено отдельной миграцией `20260909150000`; тест теперь не проглатывает
ошибку RPC, а поднимает её.

Та же ошибка повторилась и в новой миграции — обе функции этапа 8/03 сперва
оказались недоступны `service_role`, и все проверки доказательства возвращали
`false`. Второй раз причина нашлась за минуту. Вывод простой: `revoke ... from
public` без парного `grant ... to service_role` — это не ужесточение, а поломка.
