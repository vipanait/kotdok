## Найдено и исправлено по дороге

**PKCE деградировал до `plain`.** В логе висело `WARN WebCrypto API is not supported. Code challenge method will default to use plain instead of sha256`. По исходнику `@supabase/auth-js` (`helpers.js`, `generatePKCEChallenge`) видно, что без `crypto.subtle` функция возвращает verifier вместо его хеша: challenge равен verifier, и перехваченный код может обменять тот, кто его перехватил. Там же `generatePKCEVerifier` при отсутствии `crypto` строит verifier из `Math.random`. Обе дыры закрыты полифилом на `expo-crypto`.

Первая версия полифила сделала хуже: она давала только `subtle`, а клиент решает по наличию самого `crypto` и затем зовёт `getRandomValues` — вход стал падать с `TypeError: undefined is not a function`, браузер не открывался. Исправлено: обе операции ставятся вместе, существующие реализации не затираются.

**Яндекс отвечал `server_error`.** Пользователь видел «Провайдер не подтвердил вход», причина не показывалась. Добавлена диагностика: в dev-сборке причина уходит в лог (кода обмена и токенов там нет). Она и назвала виновника — `Error getting user email from external provider`: Supabase ждёт `sub` и `email`, а Яндекс отдаёт `id` и `default_email`.

Владелец указал, что в production `custom:yandex` смотрит не на Яндекс напрямую, а на собственный маршрут `https://lapka.my/api/auth/yandex/userinfo`, который переименовывает поля (`apps/web/src/server/auth/yandex-userinfo.ts`). Тот же адрес поставлен в staging — вход заработал сразу.

## Решения владельца

- **Отмена входа ничего не сообщает.** Сначала было сделано нейтральное «Вход отменён»; на живом экране это читалось как претензия к действию, которое человек совершил сам.
- **Staging зависит от production.** Userinfo staging-провайдера указывает на `lapka.my`. Альтернатива — Edge Function внутри staging-проекта — была написана и проверена локально (`deno run`, ответы 401 без заголовка и проброс ошибки Яндекса), но отброшена: владелец выбрал более простой путь для тестового контура. Следствие: вход Яндексом на staging перестанет работать, если production недоступен, и Яндекс-токен staging-пользователя проходит через продовый деплой.
- **Автоматическое связывание аккаунтов оставлено включённым.** Вход Яндексом не создал новый профиль, а прицепился к существующему email-аккаунту с тем же адресом: identities стали `email, custom:yandex`. Это то, что пункт 5/05 запрещает делать по совпадению адреса; решение владельца — пока оставить.

## Не проверено

- **Android.** SDK не установлен, устройства нет. Именно на Android разделение путей возврата (`lapka://auth/provider` против `lapka://auth/callback`) решает реальную гонку: Custom Tabs отдают ссылку и системе тоже. На iOS этой гонки не видно.
- **Реальные устройства.** Симулятор не заменяет проверку возврата в приложение после сворачивания и холодного старта.
- **Неверный `state` и повторный код** — на живом провайдере не воспроизводились; покрыты автоматическими тестами с подменённым браузером и клиентом.
