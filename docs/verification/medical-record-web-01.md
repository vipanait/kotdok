## Что сделано

- `/pets/[id]` — медкарта. Сервер проверяет, что питомец принадлежит вошедшему, через `getPet`: чужой, удалённый и неверный id дают 404 ещё до отрисовки. Затем страница читает `getHealthOverview` и последние три проверки питомца (`listChecks`) общим API-клиентом `@lapka/shared`.
- Токен Bearer берётся из сессии Supabase самого сайта (`features/api/browser-api.ts`). Хранилище токенов мобильного приложения не копируется.
- Отдельный `getPet` в браузере не вызывается: по контракту `overview.pet` — это ровно ответ `GET /pets/{id}`, второй запрос дублировал бы его.
- Состав страницы — по макету `medical` / `medical-empty`:
  - шапка: вид, порода, возраст, стерилизация, вес с трендом;
  - «Сроки»: первые три, остальные посчитаны;
  - «Важно знать»;
  - четыре раздела карточками по две строки;
  - вес: график и текстовая альтернатива;
  - «История проверок»: карточка — целиком ссылка-блок.
- Правила сроков, веса и курсов — один источник для мобильного и веба в portable-модулях `packages/shared/src/medical-record/`:
  - `record-overview.ts`: календарные дни, `localToday`, сроки (`dueEntries`, `dueTiming`: 14 дней «скоро», «с даты» после двух месяцев), группы паразитов, период и тренд веса, текущие курсы;
  - `weight-chart.ts`: раскладка графика по §7.8 (ось от минимума −10%) и круглые значения линий `chartTicks`.

  Мобильное приложение переведено на них: `calendar-day.ts` реэкспортирует общие функции, копии в `due.ts`, `weight.ts`, `medications.ts` удалены. Поведение мобильного сохранено. Тексты — в словарях каждого приложения. `today` на вебе — день по часам браузера владельца.
- Состояния — `record-load.ts`, чистый редьюсер:
  - загрузка — скелетон макета `loading`;
  - первая загрузка не удалась — ошибка с «Повторить», медкарта не рисуется;
  - обновление не удалось — прежние данные и баннер макета `load-error`;
  - 404 — «Медкарта недоступна»;
  - 401 — «Сессия закончилась»: данные и кэш сбрасываются;
  - аккаунт в удалении — переход на `/account-deletion`.

  Кэш — только в памяти вкладки, в хранилище браузера ничего не пишется.
- Флаг этапов — один объект `MEDICAL_RECORD_STAGE` в `features/medical-record/stage.ts`. Раздел открыт, только когда его включил этап и сервер указал его в `writable`. На MW-01 всё выключено. Поэтому скрыты:
  - «Добавить запись» и «Для врача»;
  - «Все →» у разделов;
  - «Сделано» и «Все сроки».

  Вместо «Все сроки» — текст «Ещё N сроков». Там же маршруты следующих этапов (`medicalRecordHref`).
- Список питомцев и обзор ведут на `/pets/[id]`. Анкета `/pets/[id]/edit` не изменилась, только её ссылка «назад» ведёт в медкарту.

### Почему падает `schema.test.ts`

Падают два утверждения, оба — точное сравнение списка объектов схемы с ожидаемым:
- `migrated schema > creates every table the tests rely on` (`schema.test.ts:116`, `expect(rows.map((row) => row.table_name)).toEqual(REQUIRED_TABLES)`). Лишняя строка в полученном — `"personal_data_consents"`.
- `migrated schema > creates every credit and triage function, and no payment ones` (`schema.test.ts:162`, `expect(rows.map((row) => row.proname)).toEqual(REQUIRED_FUNCTIONS)`). Лишняя строка — `"pd_consent_version_is_current"`.

Откуда эти объекты:
- Локальный стек Supabase общий для всех worktree. Параллельно работает `/Users/skyeng/dev/petcheck/kotdok-web-hide-google-apple` (ветка `feature/web-hide-google-apple`).
- В этой ветке есть коммит `eed8e98` «Consent: table, profile flag and sign-up trigger» (26.09.2026 15:33). Он добавляет миграцию `supabase/migrations/20260926120000_personal_data_consents.sql`, а в свой `schema.test.ts` — ожидание этих объектов (+3 строки).
- В базе есть и колонка `profiles.pd_consent_required` из той же миграции.
- Этой миграции в нашей ветке нет. В `supabase_migrations.schema_migrations` её версии тоже нет: список применённых версий совпадает с `supabase/migrations/` нашей ветки один в один. Значит, SQL применили напрямую из той ветки, минуя учёт миграций.

## Дефекты и непроверенное

1. **HTTP-статус чужого питомца — 200, а не 404.** Страница 404 показывается, данных нет. Но `pets/loading.tsx` начинает поток до `notFound()`, и Next.js 16 после этого не меняет статус (документация `loading.md`, «Status Codes»: в поток добавляется `noindex`). Так же ведёт себя и существующая `/pets/[id]/edit`. API отвечает честным 404. Исправление, если статус нужен: проверка в `proxy.ts` или отдельный `loading` без потока.
2. **Экран «Что добавить?» (`add`) не создан.** На MW-01 нет ни одной готовой формы, и выбор из нуля пунктов был бы пустым экраном. Маршрут `medicalRecordHref.add` и `addableRecordTypes()` готовы, экран добавит MW-02 вместе с первой формой (вес).
3. **Баннер «Начнём с заботы» для пустой медкарты** (7.3 спецификации, макет `medical-empty`) не показывается. Его единственное действие — «Добавить прививку», а оно появится на MW-03. Без действия баннер звал бы к тому, чего нельзя сделать. Нужно сделать на MW-03.
4. **«История проверок» без «Все».** Отдельной страницы истории питомца (`pet-history`) ни в одном этапе нет. Общая `/checks` не фильтрует по питомцу. В карточке — три последние проверки, вся история — через «История» в навигации.
5. **Закреплённые действия над нижним меню (≤760 px) не проверены вживую:** на MW-01 действий нет. CSS готов, проверить на MW-02.
6. **Не проверялись:** экранный диктор (VoiceOver/NVDA), шрифт 200%, 360×640 «шапка и сроки без скролла» (§10) и реальный iPhone Safari. Ширины 360 и 320 проверены только на горизонтальный скролл.
7. **Графики на мобильном тоже изменились.** Линии теперь стоят на круглых значениях из `chartTicks`, а не на краях оси с округлёнными подписями. Это исправление той же ошибки, что была на вебе; в симуляторе не проверено.
8. **`verify.mjs` не входит в CI.** Ему нужны Playwright и Chrome вне репозитория (переменные `PLAYWRIGHT`, `CHROME`), запущенный сайт и демо-данные.
9. **Возраст 0 в шапке.** Веб его не показывает, как и существующий список питомцев на вебе (`petSummary`: 0 — незаполненное поле). Мобильное показывает «0 лет». Это правило текстов шапки, а не общих расчётов: вынесено отдельным открытым вопросом.
