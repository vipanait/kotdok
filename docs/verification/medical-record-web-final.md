## Что получилось

- Веб показывает ту же медкарту, что приложение: одни endpoints `/api/v1/pets/…/health`, один клиент `packages/shared/src/api-client.ts`, одни правила (`packages/shared/src/medical-record/`: сроки, вес и график, курсы, календарные дни, записи форм, сводка, строка срока, подсказки анкеты, проверка ответа «Сделано»). Мобильное приложение переведено на эти же правила — копий расчётов в нём не осталось.
- Правило владельца от 26 сентября выполняется на сервере: выполненные прививки и обработки, состоявшиеся визиты и завершённые курсы не изменяются (`record_done`), удаление с подтверждением остаётся. С MW-09 отказ проверяется и внутри SQL-записи, так что правка, прочитавшая план до «Сделано» с другого устройства, тоже получает `record_done`. Приложение и веб скрывают «Изменить» у таких записей.
- Все операции ограничены владельцем на сервере; чужой питомец — 404 (страницы питомца — настоящий HTTP 404 с MW-08).
- Сохранения: ожидание, ошибка с сохранёнными полями, защита от повторной отправки. Прививки, обработки, «Сделано» (с MW-09 и у плана из одной позиции), визиты, курсы и **вес** (с MW-09, необязательный `Idempotency-Key`) повторяют сохранение с тем же ключом, новая операция — новый ключ. Без ключа остаётся только прежняя анкета питомца (`PUT /api/pets/[id]` перезаписывает поля).
- Веб не просит разрешение на уведомления, не регистрирует service worker, не шлёт email-напоминаний; напоминания веба — только строка срока и «Сроки».
- **Миграции** (MW-09, до MW-09 их не было): `20260927100000_record_done_in_sql.sql`, `20260927110000_completion_key_and_clearing.sql`, `20260927120000_medication_batch_position.sql`, `20260927130000_weight_keys_and_dating.sql` — `git diff $(git merge-base origin/main HEAD)..HEAD --stat -- supabase/` показывает ровно эти 4 файла. Вся цепочка из 46 миграций применяется к пустой базе (проверено в одноразовой базе, MW-09).
- **Контракт** изменён только аддитивно: необязательный `?today=` у `GET /health/summary` (MW-07), у `GET /health`, записей курсов и визитов, `POST /checks` и изменения курса (MW-09); необязательный `Idempotency-Key` у POST/PATCH веса и код `idempotency_key_reused` (MW-09); `visit_kind` в `/pets/due` (MW-09); `reauth_required` в 401 (MW-09); OpenAPI обновлён. Зависимости не менялись (`package-lock.json` совпадает с `origin/main`).

## Чек-лист выпуска

Порядок (решение контроллера MW-09): **`db push` staging → `db push` production → проверка fingerprint → EAS Update production → слияние PR #53 (Vercel выкладывает production) → проверка production.** Слияние в `main` сразу, без ручного шага, выкладывает сайт и API в production, поэтому к нему миграции уже должны быть в production-базе, а новый JS — опубликован.

1. **Миграции MW-09 — владелец, до всего остального.** Четыре файла `supabase/migrations/20260927100000…130000_*.sql`. Точные команды — в [отчёте MW-09, «Миграции для владельца»](medical-record-web-09.md#миграции-для-владельца): выполнять по одной строке и остановиться при любой ошибке. Кратко:
   - в папке с веткой `feature/medical-record-web` посмотреть `cat supabase/.temp/project-ref` (папка могла остаться связанной с production);
   - staging: `supabase link --project-ref rclnsbivyulqmvujiopv` → `cat supabase/.temp/project-ref` (должно быть `rclnsbivyulqmvujiopv`) → `supabase db push --dry-run` (ровно 4 файла) → `supabase db push` → `supabase migration list` и проверка только чтением в SQL Editor;
   - production: `supabase link --project-ref bczseshsgpzulqynvukg` → `cat supabase/.temp/project-ref` (должно быть `bczseshsgpzulqynvukg`) → `--dry-run` → `db push` → та же проверка;
   - вернуть связь: `supabase link --project-ref rclnsbivyulqmvujiopv` → `cat supabase/.temp/project-ref`.

   Миграции совместимы с сервером `origin/main`: новые параметры имеют значения по умолчанию, отказ `record_done` в SQL включается только новым сервером. Между `db push` и слиянием production работает как раньше (интеграционные тесты «an older server…», «the production server (origin/main)…»). Сразу после `db push`, ещё со старым сервером, SQL меняет два поведения и для установленных сборок: первое измерение веса с тем же значением, что в анкете, у питомца без истории даёт одну строку, а не две («Уточнить»); повтор «Сделано» с тем же ключом и другими данными у плана из одной позиции — 409 `conflict` вместо 200 со старой записью (ложного успеха нет). `supabase config push` не выполнять никогда.
2. **Проверка fingerprint.** Изменения мобильного приложения MW-09 — только JS (нативных модулей, `app.json` и `package.json` не меняли). В `apps/mobile`: `npx expo-updates fingerprint:generate --platform ios` и сверить с `runtime.version` установленной сборки в `eas build:list`. Если не совпадает — обновление никуда не дойдёт; остановиться.
3. **EAS Update в канал `production` до слияния.** `npm run update:production --workspace @lapka/mobile` (проект команды `vitaliypanaits-team`). Почему до слияния (проверено ревью против `origin/main` `3a6bead` и мигрированной базы):
   - новый JS работает со старым сервером: `today` уходит query-параметром, старые маршруты его не читают; заголовок `Idempotency-Key` веса старый сервер игнорирует, и `p_key` берёт значение по умолчанию `null`; старая `CompleteItemInputSchema` принимает `''` и передаёт дальше, а после `db push` пустая строка очищает поле — это и есть задуманный смысл;
   - старый сервер `record_done` не присылает, а новый JS и так скрывает «Изменить» у выполненных записей;
   - обновление применяется только после перезапуска приложения, поэтому публикация до деплоя уменьшает число устройств, на которых старый JS встретит `record_done` после слияния.
4. **Слияние PR #53** → Vercel выкладывает production.
   - С этого момента сервер отказывает в правке выполненных записей, завершённых курсов и состоявшихся визитов (`409 record_done`).
   - Устройства, ещё не перезапустившие приложение (старый JS): показывают «Изменить» у выполненных записей и визитов и получают на сохранение общую ошибку (данные не портятся); повтор «Сделано» с тем же ключом и другими данными получают 409 `conflict` (ложного успеха нет); считают день по UTC (`?today=` не шлют — сервер считает как раньше); вес шлют без ключа (как раньше).
5. **Проверить production:** вход, медкарта питомца, раздел, сводка.
6. **Свежий `main`.** `main` влит в ветку в `f0e1b9d` (#51, #52), `origin/main` с тех пор — `3a6bead`. Если `main` уйдёт дальше до слияния — слить ещё раз, `npm run openapi:update`, полный прогон тестов и `next build`.
7. **Проверить владельцу Safari на Mac** (агент им не управляет):
   - печать и «Сохранить PDF» сводки «Барона» и «Мурки»: нет меню, записи не разрезаны, имя файла с «.2026»;
   - «Назад» браузера в изменённой форме;
   - обзор с пятью питомцами на ширине окна ~1024;
   - формы.
8. **Справочник production** показывает только проверенные препараты; локальный флаг непроверенных не включать.

## Остающиеся ограничения (после MW-09)

Реальные, принятые решениями контроллера или отложенные ревью. Ни одно не выдаёт макет за готовую функцию. Что из прежнего списка закрыто в MW-09 — в следующем разделе.

**Среда и проверка**
- **Safari на Mac** не проверялся ни на одном этапе (решение контроллера). Safari на iOS проверен в iOS Simulator (MW-07 и MW-09 печать и имя PDF, MW-08 обзор, медкарта и анкета).
- **Настоящий экранный диктор** (VoiceOver/NVDA) не проверялся. Доступность проверена автоматически: имена, фокус, порядок Tab, `aria-*`, live-области. Масштаб 200 % в Chrome проверен в MW-09 (`task6-zoom200.mjs`: без горизонтальной прокрутки, перекрытий и фокуса, скрытого закреплёнными панелями; исключение — нижняя часть высокого многострочного поля, см. «Интерфейс»).
- **`verify.mjs` не в CI**: им нужны Playwright и Chrome в раннере — отдельная задача инфраструктуры.
- **Миграции MW-09** проверены на локальной базе и повтором с нуля в одноразовой базе. На staging и production их применяет владелец (чек-лист, п. 1).

**Сервер и данные**
- **Установленные сборки до EAS Update** не шлют день владельца и ключ веса. Для них сервер, как раньше, считает по UTC:
  - список лекарств анкеты, синхронизацию `p_today`, контекст анализа, сводку;
  - окно завершённого курса (с 12:00 UTC дня окончания).
  
  Повтор POST веса после смены дня у них может создать второе измерение. Прямой вызов API без `today` получает прежнее окно курса.
- «Уточнить» у веса анкеты без истории: если при датировании изменить значение, остаются две строки (новая датированная и прежняя недатированная). Датированная строка помечена `record`, не «из анкеты» (MW-09 Task 1).
- Анкета питомца по-прежнему без ключа идемпотентности: повтор перезаписывает те же поля.
- `pet_weight_requests` растёт на одну строку за каждое сохранение веса с ключом; строки удаляются каскадом с питомцем и аккаунтом.

**Интерфейс (решения и отклонения от макетов)**
- Будущий курс не входит в «Принимает сейчас» медкарты и сводки (MW-07, правило `isTakenNow`), но остаётся в списке анкеты (SQL).
- «Добавить в лекарства» у назначения визита отмечено по умолчанию (спецификация §7.11; решение контроллера MW-06).
- Обзор показывает первых трёх питомцев по порядку; срок питомца дальше третьего виден в «Все питомцы».
- «Своё название» и «Без препарата» — карточки в форме, а не отдельные экраны; адрес `…/[recordId]/complete` — дополнительный подмаршрут (MW-04).
- После сохранения записи — возврат к разделу или источнику с уведомлением и ссылкой «Открыть запись» (MW-09). Чтобы увидеть запись, нужен ещё один переход.
- После полуночи «сегодня» страниц и форм переходит на новый день, но дата по умолчанию у уже открытой новой записи остаётся вчерашней: меняются только пределы (решение контроллера MW-09).
- Пустое начало курса допустимо только у курса, у которого начала нет в данных (`started_on === null`). Такой курс можно оставить без начала при правке (решение MW-09).
- Строка срока по §7.1 («Обработка от блох и клещей — просрочено», «Визит к врачу: осмотр — через 2 дня»): на узком экране обрезается название, статус виден всегда. На телефоне зазор перед «—» чуть шире задуманного.
- Страницы записи и `health/new` без скелета загрузки: при переходе без предзагрузки навигация ждёт серверную проверку — цена настоящего HTTP 404 (MW-09).
- Защита «Назад» держится на истории браузера (у Next 16 нет штатного перехвата). В Chrome проверена полностью. Без Navigation API копия после перезагрузки узнаётся эвристикой; переход меню истории на копию требует двух «Назад»; копия может остаться в истории «вперёд». Safari и Firefox не проверялись.
- Печать:
  - в Chrome с полями дисклеймер на первой странице дважды (строка под заголовком и поле страницы; решение MW-09);
  - Safari на iOS печатает примерно ×1,2: Мурка там 2 страницы (в Chrome — 1), у Барона на стр. 1 около 40 % пусто; дисклеймер в Safari — строка на стр. 1 плюс колонтитул самого Safari с адресом страницы;
  - проверка печатается одной строкой (§7.17) и может скрыть часть симптомов — полный текст на экране;
  - Chrome с включёнными «Колонтитулами» и Firefox не проверялись.
- Многострочное поле (заметка, причина визита) при 200 % или на узком окне: Chrome по Tab показывает каретку, а не всё поле. Верх поля виден, а нижняя часть высокого поля может остаться под нижней навигацией. WCAG 2.4.11 AA это допускает (MW-09 Task 7).

**Только код и тесты** (на владельца не влияют) — перечислены в [отчёте MW-09](medical-record-web-09.md#остающиеся-ограничения). Главное:
- компонентные тесты без jsdom не исполняют эффекты (нужна новая зависимость — решение владельца);
- SQL повторяет правило `changesCourse`;
- `ApiErrorCode` принимает любую строку.

## Закрыто в MW-09 (было в этом списке 26 сентября)

Сервер и данные:
- Гонка «прочитать и записать» (правка плана после «Сделано»/«Состоялся»/«Завершить курс» с другого устройства) — отказ `record_done` внутри SQL под блокировкой питомца (`f0f12b0`, `51b119b`).
- Повтор «Сделано» с тем же ключом и другими данными у плана из одной позиции — 409 `conflict` (`f0f12b0`).
- Клинику и заметку плана при «Сделано» можно очистить: пустое поле очищает, не переданное оставляет текст плана (`f0f12b0`).
- Завершённый курс защищается по дню владельца, если приложение его прислало; день владельца только ужесточает окно (`f0f12b0`, `51b119b`).
- Вес — необязательный `Idempotency-Key`; повтор после смены дня не создаёт второго измерения (`f0f12b0`, `51b119b`).
- Повтор пакета лекарств возвращает курсы в порядке ввода; `GET /health` тоже держит порядок пакета (`f0f12b0`, `e3dcba0`).
- «Уточнить» у веса анкеты без истории: то же значение с датой — одна строка (`f0f12b0`; оговорка о другом значении — выше).
- По UTC больше не считаются (для сборок после EAS Update и для сайта): список лекарств анкеты в `GET /health`, `p_today` синхронизации списка, контекст анализа (`e40d786`).
- Настоящий HTTP 404: несуществующая запись своего питомца, `?check=` чужой проверки, `/checks?pet=<чужой/удалённый>`; `/edit` сделанной записи — HTTP 307 (`e40d786`).

Интерфейс:
- Веб и телефон одинаково требуют дату начала нового курса (`8c5e38b`).
- Своё название без интервала — запасной интервал и на вебе (`fdb7f58`).
- Возраст 0 — «0 лет» везде: шапка, сводка, списки, веб и телефон (`fdb7f58`, `7a4d503`).
- Строка срока называет срок по §7.1 и вид визита (`e40d786`); статус не обрезается (`e4e7ffe`).
- После сохранения — к разделу или источнику с уведомлением и ссылкой на запись (`fdb7f58`).
- «Сделано» — отдельный диалог подтверждения с позицией и датой (`fdb7f58`).
- «Назад» браузера в изменённой форме спрашивает (`fdb7f58`, `7a4d503`, `8c4557e`).
