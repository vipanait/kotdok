# Дизайн 5/01 — вход через Google и Яндекс в мобильном приложении

Дата: 8 сентября 2026. Источник требований: [дорожная карта](../../mobile-api-plan.md), пункт **5/01**.
Отчёт по этапу: `docs/verification/stage-5.md` (будет создан).

## Что решаем

Кнопки «Войти с Яндекс ID» и «Продолжить с Google» на экранах входа и регистрации нарисованы, но
ничего не делают: `onPress` пустой, в accessibility они помечены недоступными. Причина была
внешняя — в тестовом Supabase не было включённых провайдеров. 8 сентября 2026 оба включены
(`custom:yandex` и Google), и запрос авторизации уходит провайдеру с правильным `redirect_uri`.
Значит, кнопки можно подключать.

## Граница этого захода

Только 5/01. Apple (5/02–5/07) не берём: доступа к Apple Developer нет и в ближайшее время не
будет, а без него эти пункты всё равно упираются в приёмку. Связывание аккаунтов (5/05) и ротация
секретов (5/09) — отдельный заход.

Проверка: симулятор iOS (Xcode 26.6, iPhone 17 Pro). Реальных устройств нет, Android SDK снят
коммитом «Take the Android toolchain back out», поэтому Android остаётся NOT RUN, а iOS — PARTIAL:
симулятор не заменяет устройство. Ввод учётных данных в формы Яндекса и Google выполняет владелец
проекта; агент доводит приложение до экрана провайдера и фиксирует, что вернулось.

## Решение

Системный браузер через `expo-web-browser`:

1. `supabase.auth.signInWithOAuth({ provider, options: { redirectTo, skipBrowserRedirect: true } })`
   — Supabase готовит PKCE-verifier и отдаёт адрес авторизации, но никуда не уходит сам.
2. `WebBrowser.openAuthSessionAsync(url, redirectTo)` — `ASWebAuthenticationSession` на iOS,
   Custom Tabs на Android. Адрес возврата приходит **в вызвавший код**, а отмена — явным
   `{ type: 'cancel' }`.
3. `supabase.auth.exchangeCodeForSession(code)` — сессия, дальше работает то, что уже есть:
   `onAuthStateChange` в `AuthProvider`, редирект со входа на список питомцев, хранение в Keychain.

Отвергнутые варианты: `Linking.openURL` с разбором в глобальном слушателе ссылок (об отмене узнать
нельзя — пользователь закрывает браузер, приложение остаётся со спиннером навсегда) и нативные SDK
провайдеров (5/01 прямо требует системный браузер; для Яндекса Supabase не принимает id_token).

## Адрес возврата: отдельный путь

Провайдерский вход возвращается на `lapka://auth/provider`, а не на `lapka://auth/callback`,
который используют письма подтверждения и восстановления.

Причина техническая. На Android Custom Tabs отдаёт ссылку и системе тоже, поэтому глобальный
слушатель в `app/_layout.tsx` увидит тот же адрес и попытается обменять тот же код второй раз.
Первый обмен уже израсходовал код, второй вернёт ошибку — и пользователь увидит сообщение о сбое
после успешного входа. Разные пути убирают эту гонку без флагов и таймеров: `parseAuthLink`
возвращает `null` для неизвестного пути, то есть просто игнорирует ссылку (поведение уже покрыто
тестом «unknown path»).

Требовалось действие в панели Supabase — добавить `lapka://auth/provider` в Redirect URLs
staging-проекта; без него Supabase подменил бы адрес возврата на Site URL и приложение ссылку не
получило бы. Владелец сообщил, что адрес добавлен 8 сентября 2026; фактическую запись подтвердит
первый живой вход.

## Модуль `src/lib/provider-sign-in.ts`

Одна ответственность: провести обмен и вернуть исход, о котором экран может рассуждать. Нативные
модули и клиент Supabase приходят параметрами, поэтому чистая часть тестируется без симулятора.

```ts
export type ProviderId = 'google' | 'custom:yandex'

export type ProviderOutcome =
  | { kind: 'session' }             // вход состоялся
  | { kind: 'cancelled' }           // пользователь закрыл браузер
  | { kind: 'failed'; message: string }
```

Внутри — четыре шага и одна проверка: вернувшийся адрес принимается, только если это наша схема и
наш путь. Чужой адрес не обменивается и считается ошибкой, а не поводом доверять параметрам.

`AuthProvider` получает `signInWithProvider(provider): Promise<ProviderOutcome>` рядом с существующими
`signIn` и `signUp`; экраны продолжают ходить через контекст, а не звать Supabase напрямую.

## Поведение на экране

- Нажатие: спиннер на нажатой кнопке, вторая на это время заблокирована.
- `cancelled`: возвращаемся на экран входа и показываем нейтральное «Вход отменён» — `Banner` с
  тоном `info`, а не `error`. Решение владельца от 8 сентября 2026: человек должен видеть, что
  приложение поняло его действие, а не гадать, почему ничего не произошло. Отмена при этом не
  окрашивается как сбой.
- `failed`: тот же `Banner` с тоном `error` — там же, где показываются ошибки email-входа.
- Успех: ничего не делаем руками. Сессия появляется, `sign-in.tsx` сам делает `Redirect` на питомцев.

Кнопки перестают быть `disabled` в accessibility и получают настоящий `onPress`.

## Ошибки, которые обязаны отклоняться

| Случай | Что делает приложение |
| --- | --- |
| Пользователь закрыл браузер | `cancelled`, экран входа, нейтральное «Вход отменён» |
| Провайдер вернул `error=access_denied` | `failed` с текстом, сессии нет |
| Адрес возврата чужой схемы или чужого пути | `failed`, обмена кода не происходит |
| Ответ без кода | `failed`, сессии нет |
| Повторный обмен того же кода | ошибка Supabase → `failed`, прежняя сессия не меняется |

## Проверки

Автоматически (vitest, подменённые браузер и клиент Supabase): успешный обмен, отмена, ошибка
провайдера, чужой redirect, ответ без кода, повторный код, `signInWithOAuth` вернул ошибку.
Внешние провайдеры в CI не вызываются.

Вручную на симуляторе: вход Яндексом, вход Google, отмена на экране провайдера, повторный вход
после выхода. Фиксируются скриншоты и запись в `docs/verification/runs/stage-5/`.

## Риски

- **Разбор профиля Яндекса.** У `custom:yandex` пустой `attribute_mapping`, а Яндекс отдаёт `id` и
  `default_email` вместо `sub` и `email`. Если вход упадёт на получении профиля, чинится настройкой
  провайдера в Supabase, а не кодом; узнаем это только на живом входе.
- **Android не проверяется.** Код для обеих ОС одинаковый, но утверждать, что Custom Tabs ведут себя
  как ожидается, будет нечем. В отчёте — NOT RUN, и это не «когда-нибудь»: проверка Android
  записывается обязательным долгом этапа в `docs/verification/OPEN_QUESTIONS.md`, потому что именно
  на Android разделение путей возврата решает реальную гонку, а на iOS её попросту не видно.
- **Симулятор не устройство.** Возврат в приложение после сворачивания и поведение при холодном
  старте на настоящем телефоне остаются непроверенными.

## Вне объёма

Apple во всех видах, связывание способов входа, повторное подтверждение личности перед удалением,
ротация client secret, нативные SDK провайдеров, вход провайдером на сайте (там он уже работает).
