# Дизайн 8/05 — обработчик удаления аккаунта (без отзыва Apple)

Дата: 17 сентября 2026. Источник требований: [дорожная карта](../../mobile-api-plan.md), пункт **8/05**.
Отчёт: `docs/verification/stage-8.md` (дополняется). Порядок шагов и состояния задачи:
[jobs-uploads-deletion.md](../../architecture/jobs-uploads-deletion.md), раздел 4. Порядок таблиц:
[deletion-data-map.md](../../architecture/deletion-data-map.md).

## Что решаем

Заявка на удаление принимается с 9 сентября: аккаунт сразу становится `deleting`, записывается
задача в `deletion_jobs`, человек получает квитанцию. Дальше ничего не происходит — данные никто не
удаляет. 17 сентября на production это пришлось делать руками: пустой дубликат аккаунта удаляли
в панели Supabase, сначала профиль, потом пользователя. Опубликованный срок удаления — 30 дней, и
без обработчика он не выполняется.

## Граница

Берём: выполнение задачи удаления с сохранением прогресса, повторы после сбоя, ежедневную
подстраховку по крону, архив финансовых записей из схемы `retired`.

**Не берём, решение владельца от 17 сентября 2026:**

- **Отзыв Apple-токена (5/06–5/07).** Apple пишет, что приложения со входом через Apple *should*
  отзывать токены через REST API, а не *must*; ручное или долгое удаление Apple допускает. Отзыв
  требовал отдельного окна Apple на странице удаления, приватных ключей Apple в Vercel и хранения
  токена в зашифрованном виде. Остаётся открытым риском: после удаления Лапка остаётся в списке
  «Вход с Apple» в настройках Apple ID человека, пока он не уберёт её сам.
- **Уведомление поддержки о застрявших задачах (9/06).**
- **Файлы Storage (8/08) и резервные копии (8/09)** — пользовательских файлов нет до этапа 6, копий
  на Free-плане нет.
- **Срок хранения финансового архива (1.7)** — `purge_after` по-прежнему пуст.

## Найдено при проектировании

Сверка внешних ключей на локальной базе 17 сентября: кроме `credit_ledger`, удаление блокируют две
таблицы, оставшиеся от оплат и перенесённые в схему `retired` 10 сентября:

| Таблица | Ссылка | При удалении |
| --- | --- | --- |
| `retired.transactions.user_id` | `auth.users` | **RESTRICT** |
| `retired.credit_transactions.user_id` | `profiles` | **NO ACTION** |

`archive_account_financials` после 10 сентября архивирует только `credit_ledger`. Аккаунт с любой
старой транзакцией сейчас не удаляется вовсе. Обе таблицы архивируются так же, как записи
баланса: в `financial_archive` с источниками `transactions`, `transaction_status_events` и
`credit_transactions`, которые ограничение архива уже разрешает. История статусов транзакции
уходит в архив до самой транзакции, потому что удаляется вместе с ней каскадом.

Отдельно: на production применена миграция `20260910090000_check_job_queue` из незаконченной ветки
`server/stage-6-job-reliability`, которой нет в `main`. Номер новой миграции должен быть позже неё.

## Решение

### База

Одна миграция, `20260917120000_deletion_worker.sql`:

- `deletion_jobs.attempts integer not null default 0` и `deletion_jobs.lease_until timestamptz`.
- `claim_deletion_job(p_user_id uuid, p_lease_seconds integer) returns jsonb` — одним `update`
  захватывает задачу в статусе `pending` или `in_progress`, если её аренда свободна или истекла:
  ставит `in_progress` и `lease_until = now() + lease`. Возвращает `progress` захваченной задачи
  или `null`, если захватить нечего. Два одновременных обработчика не получат одну задачу.
- `mark_deletion_step(p_user_id uuid, p_step text) returns void` — записывает в `progress` ключ
  шага со временем. Шаги: `data`, `auth`.
- `record_deletion_failure(p_user_id uuid, p_error_code text, p_max_attempts integer) returns text` —
  увеличивает `attempts`, пишет `error_code`, снимает аренду; при `attempts >= p_max_attempts`
  ставит `action_required`, иначе оставляет `in_progress`. Возвращает новый статус.
- `due_deletion_jobs(p_limit integer) returns setof uuid` — задачи `pending`/`in_progress` со
  свободной или истёкшей арендой, старые первыми.
- `delete_account_data(p_user_id uuid) returns void` — всё в одной транзакции и безопасно при
  повторе:
  1. `archive_account_financials(p_user_id)` (удаляет `extra_check_requests`, архивирует и удаляет
     `credit_ledger`);
  2. архив и удаление `retired.transaction_status_events` и `retired.transactions` пользователя;
  3. архив и удаление `retired.credit_transactions`;
  4. удаление `symptom_checks` (`check_jobs` уходят каскадом), `pets` (включая помеченных
     `deleted_at`), `profiles` (`user_feedback` уходит каскадом).
- Все функции `security definer`, `set search_path = public`, выполнять может только `service_role`.

`complete_deletion_job` и `purge_expired_deletion_jobs` уже есть. Аренду при завершении снимать не
нужно: задачу в статусе `completed` никто не захватывает.

### Обработчик

`apps/web/src/server/account/deletion-worker.ts`, без `next/*`:

```
processDeletionJob(deps, userId) -> 'completed' | 'retry' | 'action_required' | 'not_claimed'
```

1. `claim` — не захватил: `not_claimed`, ничего не делает.
2. Если в `progress` нет `data`: `deleteAccountData`, затем `markStep('data')`.
3. Если нет `auth`: `deleteAuthUser`; «пользователь не найден» считается успехом; затем
   `markStep('auth')`.
4. `complete` с опубликованным сроком хранения записи (`DELETION_RECORD_RETENTION_DAYS`).
5. Любая ошибка шага: `recordFailure(код шага, 5)`; результат `retry` или `action_required`.
   Ошибка не пробрасывается и не выдаётся за успех; в журнал пишется только код шага, без user id
   и без текста ошибки от базы.

Зависимости передаются параметром; `createDeletionWorkerDeps(supabase)` собирает настоящие поверх
RPC и `auth.admin.deleteUser`. Аренда — 120 секунд, предел попыток — 5.

### Запуск

- **Сразу после заявки.** Оба маршрута заявки (`/api/v1/account-deletion` и `/api/account-deletion`)
  после ответа `202` вызывают `scheduleDeletionProcessing(userId)` из
  `server/account/deletion-after.ts` — адаптер над `after()` из `next/server`, добавляется в список
  адаптеров `service-boundaries.test.ts`. Внутри — `processDeletionJob` с настоящими зависимостями.
- **Раз в сутки.** `vercel.json` получает `crons: [{ "path": "/api/cron/deletion-jobs", "schedule":
  "0 3 * * *" }]`. Маршрут `GET /api/cron/deletion-jobs` сверяет заголовок
  `Authorization: Bearer ${CRON_SECRET}` сравнением постоянного времени (нет секрета в окружении или
  не совпал — `401`), затем обрабатывает до 20 задач из `due_deletion_jobs` по очереди и вызывает
  `purge_expired_deletion_jobs`. Отвечает счётчиками, без user id. `maxDuration = 60`.

### Что видит человек

Ничего нового. Статус по квитанции уже различает `pending`, `completed` и `action_required`:
через секунды после заявки он обычно `completed`; при сбое остаётся `pending` до следующей попытки;
после пяти неудач — `action_required`.

## Проверки

Интеграционные, на настоящем локальном Supabase (`npm run test:integration`):

1. Пустой аккаунт: после обработки нет ни профиля, ни пользователя Auth; задача `completed`,
   `retain_until` выставлен.
2. Наполненный аккаунт: питомцы, в том числе помеченный удалённым, проверки, задачи анализа,
   записи баланса, заявка на доп. проверку, отзыв, старая транзакция с историей статусов и запись
   `retired.credit_transactions` — всё удалено, финансовые записи лежат в архиве.
3. Данные второго пользователя не изменились ни в одной таблице.
4. Сбой на шаге данных и на шаге Auth: задача `in_progress`, `attempts = 1`, данные не
   полуудалены; следующий запуск завершает без повторного удаления того, что уже удалено.
5. Два запуска одновременно: один `completed`, второй `not_claimed`; удаление одно.
6. Пять неудач подряд: `action_required`; статус по квитанции `action_required`, не `completed`.
7. Маршрут заявки планирует обработку ровно один раз (планировщик подменён в тесте).
8. Крон: без секрета и с неверным — `401`; с верным — обрабатывает задачи и чистит просроченные.
9. `schema.test.ts`: новые функции внесены в закреплённый список.

Модульные: порядок шагов, продолжение по `progress`, «пользователь не найден» как успех, коды
ошибок по шагам.

Вручную на staging: заявка на удаление наполненного тестового аккаунта из приложения; через
минуту статус `completed`; в базе нет его строк, в архиве есть его финансовые записи.

## Развёртывание

Урок 0.3: миграция накатывается **до** выкатки кода, который её вызывает.

1. Миграция на staging, затем на production — с согласия владельца.
2. `CRON_SECRET` в переменных Vercel для Production — вписывает владелец.
3. Мердж и выкатка.
4. Ручная проверка на staging.

## Риски

- **Apple-согласие остаётся** после удаления (см. «Не берём»). Если App Review спросит — отдельная
  задача по 5/06–5/07.
- **`after()` может не дожить до конца** при ограничении времени функции Vercel. Шаги короткие, а
  недоделанную задачу подберёт суточный крон; человек до этого видит `pending`.
- **Крон раз в сутки на Hobby** срабатывает в течение указанного часа, не в минуту. Для срока в 30
  дней это не важно.
- **Расхождение миграций production и `main`** (`check_job_queue`). Не мешает этой работе, но
  записывается в открытые вопросы.
