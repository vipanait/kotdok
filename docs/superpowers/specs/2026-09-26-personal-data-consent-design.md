# Дизайн: согласие на обработку персональных данных

Дата: 26 сентября 2026. Этап дорожной карты: **12** ([mobile-api-plan.md](../../mobile-api-plan.md)).
Отчёт по этапу: `docs/verification/stage-12.md` (будет создан).

## Что решаем

С 1 сентября 2025 года согласие на обработку персональных данных оформляется отдельным
документом и не может быть частью пользовательского соглашения (ч. 1 ст. 9 152-ФЗ в редакции
156-ФЗ). Доказывать, что согласие получено, обязан оператор (ч. 3 ст. 9).

Сейчас:

- на вебе при регистрации одна галочка «Я принимаю пользовательское соглашение», в мобилке —
  строка «Продолжая, вы принимаете…»; отдельного согласия нет нигде;
- ничего не записывается в базу;
- вход через Яндекс с `/login` создаёт аккаунт без единой галочки;
- политики обработки персональных данных нет, а раздел 5 соглашения неполон (упоминает только
  OpenAI и Supabase, не упоминает фото, медкарту, Vercel, провайдеров входа).

## Решения владельца

- Одна галочка — только за согласие на обработку ПДн. Соглашение принимается нажатием кнопки
  (акцепт действием, ст. 438 ГК), строкой под кнопкой.
- Сразу веб и мобилка.
- Экран согласия — только для новых аккаунтов. Все, кто зарегистрирован до выкладки, согласие
  не дают.
- Оператор в текстах — «Администрация Сервиса», без реквизитов.
- Получатели данных называются, страны — нет.

## Граница

Входит: запись согласия, экран-страховка, серверная проверка, тексты (политика, согласие,
правка раздела 5 соглашения), веб и мобилка.

Не входит: локализация базы в России, уведомления в Роскомнадзор, реквизиты оператора,
английские версии текстов (как и соглашение, они только на русском с плашкой для en-интерфейса),
урезание профиля Яндекса до одной почты (отдельная задача).

## Данные

Миграция `…_personal_data_consents.sql`:

```sql
create table public.personal_data_consents (
  id          bigint generated always as identity primary key,
  user_id     uuid not null references auth.users(id) on delete cascade,
  version     text not null,
  source      text not null check (source in ('web', 'ios', 'android')),
  accepted_at timestamptz not null default now(),
  unique (user_id, version)
);

alter table public.profiles add column pd_consent_required boolean not null default false;
alter table public.profiles alter column pd_consent_required set default true;
```

- Все существующие строки `profiles` получают `false` — «только новые». Новые профили — `true`.
- RLS включён, политик для `anon`/`authenticated` нет: читает и пишет только сервер
  (service role) и триггер, как и во всех таблицах после `20260906000000`.
- Записи не правятся. Удаляются только вместе с `auth.users` при удалении аккаунта;
  `docs/architecture/deletion-data-map.md` получает строку про таблицу.
- `public.pd_consent_version_is_current(v text) returns boolean` — список действующих редакций.
  Новая редакция текста = новая миграция, переопределяющая функцию.

Действующая редакция в коде — `PD_CONSENT_VERSION = '2026-09-26'` в `packages/contracts`.
Интеграционный тест сверяет, что база принимает именно её.

## Правило «согласие нужно»

`pd_consent_required = true` **и** нет записи с `version = PD_CONSENT_VERSION`.

Считается в `loadAccount` (`apps/web/src/server/auth/account-state.ts`) — там же, где уже
решается «аккаунт удаляется». Новая редакция текста поэтому снова показывает экран тем, у кого
флаг `true`; старые аккаунты её не увидят.

## Как согласие попадает в базу

**Регистрация по почте (веб и мобилка).** Клиент кладёт в метаданные
`pd_consent: { version, source }`. `handle_new_user` записывает согласие, если версия
действующая и источник из списка. Мусор в метаданных регистрацию не ломает и согласие не
пишет — так же сейчас устроен `locale`.

**Провайдер с экрана регистрации на вебе.** Метаданные через OAuth не передать. Перед уходом к
провайдеру страница ставит cookie `lapka_pd_consent=<версия>` (SameSite=Lax, 15 минут, путь
`/auth/callback`). Callback после обмена кода: если согласие нужно и cookie несёт действующую
версию — пишет его с `source = web`; cookie удаляет в любом случае. Cookie ставит только наша
страница, поэтому чужой сайт не может «дать согласие» за человека через подделанную ссылку.

**Провайдер с экрана регистрации в мобилке** (Яндекс, Google, Apple). Экран запоминает в
`AuthProvider` «согласие к отправке» (в памяти, не на диске). После появления сессии
экран-страховка сначала отправляет его `POST /api/v1/consent`, потом спрашивает статус.
Упавшая отправка не теряет человека: статус скажет `required`, и он увидит экран согласия.

**Экран согласия** — для всех остальных случаев: новый аккаунт через провайдера со страницы
входа, новая редакция текста, упавшая отправка.

## Сервер

Новый код ошибки `consent_required` (403) в `commonErrors`.

- `withApiAuth` отказывает с `consent_required`, если согласие нужно. Исключения (опция
  маршрута): `GET/PATCH /api/v1/me`, `/api/v1/consent`, эндпоинты удаления аккаунта.
- Веб-роуты на cookie проверяются тем же правилом через общий помощник.
- `GET /api/v1/consent` → `{ required: boolean, version: string }`.
- `POST /api/v1/consent` с `{ version, source }`: версия должна быть действующей (иначе 400 `bad_request` — в контракте нет кода 422),
  повтор не создаёт вторую запись (`on conflict do nothing`), ответ 204.
- Веб-двойник `POST /api/consent` на cookie с CSRF, `source` всегда `web`.
- `/me` не меняется: `PublicProfileSchema` строгая, и уже установленные сборки отвергли бы ответ
  с новым полем.

## Веб

- `/register`: галочка «Я даю [согласие на обработку персональных данных]» вместо галочки за
  соглашение, по умолчанию снята. Под кнопкой — «Нажимая «Зарегистрироваться» или входя через
  Яндекс ID, вы принимаете [пользовательское соглашение] и [политику обработки персональных
  данных]». Кнопка Яндекса без галочки не уходит к провайдеру (как сейчас `requireTos`).
- `/login`: та же строка про соглашение, без галочки.
- `/consent?next=…`: галочка, кнопка «Продолжить», ссылки на тексты, «Выйти» и ссылка на
  удаление аккаунта. После записи — переход на `next` (проверенный `getSafeNextPath`).
- `loadCabinetState` получает состояние `consent_required`; `requireCabinet` ведёт на
  `/consent`. Страница удаления аккаунта остаётся доступной без согласия.
- `/consent` добавляется в защищённые пути прокси.

## Мобилка

- `sign-up`: галочка согласия (свой компонент, доступный для VoiceOver как checkbox) над
  кнопкой; `LegalNote` меняет текст на «Продолжая, вы принимаете Пользовательское соглашение и
  Политику…». Кнопки провайдеров без галочки не стартуют и подсвечивают галочку.
- `sign-in`: без галочки, `LegalNote` как на регистрации.
- `app/consent.tsx` — экран вне вкладок, как `deletion-status`: галочка, «Продолжить», ссылки
  на тексты (системный браузер, production-сайт), «Выйти».
- Страховка в `(tabs)/_layout.tsx` рядом с запросом `getMe`: отправить «согласие к отправке»,
  если есть, затем `getConsentStatus`; `required` → `router.replace('/consent')`. Пока статус
  неизвестен, вкладки не рисуются.
- Ошибка `consent_required` из любого запроса тоже ведёт на `/consent` (на случай гонки).
- `packages/shared` api-client: `getConsentStatus`, `giveConsent`.

## Тексты

Все на русском, JSX-страницы по образцу `/legal`, оператор — «Администрация Сервиса», контакт —
`support@lapka.my`.

1. **Политика обработки персональных данных** — `/legal/privacy`. Разделы: оператор; чьи данные;
   какие данные (почта, профиль провайдера входа, технические данные — IP и браузер в журналах
   входа, cookies, сведения о питомцах, описания симптомов, фото, медкарта, отзывы); цели;
   правовые основания (договор — п. 5 ч. 1 ст. 6, согласие — п. 1 ч. 1 ст. 6); действия с
   данными; лица, которым поручена обработка (Supabase, Vercel, OpenAI; Яндекс, Google, Apple как
   провайдеры входа; Expo — обновления приложения; Telegram — уведомления администрации с внутренним идентификатором), трансграничная передача — без названия стран;
   сроки (до удаления аккаунта; фото удаляются после анализа, не приложенные к проверке — не позже чем через сутки, их убирает ежедневный крон);
   права субъекта и порядок обращения; отзыв согласия; cookies (только технические, перечень);
   меры защиты; изменения политики.
2. **Согласие на обработку персональных данных** — `/legal/personal-data`, редакция
   `2026-09-26`. Черновик — ниже.
3. **Соглашение** — раздел 5 заменяется отсылкой к политике и согласию; убирается «улучшение

## Новая редакция текста

Сейчас сервер принимает и требует ровно `PD_CONSENT_VERSION` (`recordConsent`, `loadAccount`), и
сервер, и приложение берут её из одной константы. Слияние выкатывает сервер сразу, а установленные
приложения до EAS Update отправляют старую редакцию — их экран согласия получит отказ, а после
отказа снова покажется. Поэтому до появления второй редакции нужно одно из двух: клиент отправляет
`version`, которую вернул `GET /consent` (ссылка всегда открывает актуальный текст), или сервер
принимает набор редакций. Код меняется вместе с первой новой редакцией.

## Совместимость и выкладка

1. Владелец применяет миграцию (`supabase db push`) до слияния — слияние в `main` сразу
   выкатывает production.
2. Слияние: веб и API. Уже установленные сборки со старым JS не знают `consent_required`: новый
   пользователь увидит общую ошибку до получения EAS Update. Существующих пользователей это не
   касается — у них флаг `false`.
3. EAS Update в канал production.
4. Нужна ли новая сборка в App Store: компоненты чистый JS, нативных модулей не добавляется —
   хватает EAS Update. Если при реализации понадобится нативный модуль — отдельный пункт.

## Тесты

- Интеграционные (локальный Supabase): триггер пишет согласие из метаданных; мусорные метаданные
  не ломают регистрацию; существующий профиль после миграции не требует согласия, новый —
  требует; база принимает `PD_CONSENT_VERSION`; каскадное удаление; `POST` идемпотентен и
  отвергает чужую версию; `withApiAuth` отдаёт `consent_required` и пропускает исключения.
- Callback: cookie с действующей версией пишет согласие и удаляется; без cookie или с чужой
  версией — не пишет.
- Контракты и OpenAPI: новые схемы и код ошибки.
- Мобилка (vitest, чистая логика): порядок «отправить отложенное → спросить статус», реакция на
  `consent_required`.
- Вручную: регистрация по почте и через Яндекс на вебе; вход через Яндекс новым аккаунтом с
  `/login` → экран согласия; старый аккаунт экран не видит; то же в симуляторе iOS
  (почта, Яндекс, Apple).
