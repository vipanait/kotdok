# Исполнимый план этапа 4 — Expo, вход по email и первый сценарий

Источник требований: [дорожная карта](../../mobile-api-plan.md), раздел «Этап 4». Отчёт: `docs/verification/stage-4.md`.

База: ветка `stage-0-baseline` после этапа 3.

## Что уже есть

- `apps/mobile` — минимальный Expo-проект, `expo-doctor` проходит 21/21, оба экспорта собираются.
- `@lapka/shared` — типизированный API-клиент, валидирующий ответы по контракту.
- `/api/v1`: `health`, `me`, `pets`, `checks`, `credits/extra-request`, `feedback`.
- Тестовый Supabase `lapka-staging` со схемой, идентичной production.

## Граница выполнимого

Приёмка 4/01–4/04 требует подписанных development builds и **реальных** iPhone и Android. Доступа к Apple Developer и Expo/EAS нет, физических устройств нет. Поэтому этап делится надвое:

- **Выполнимо сейчас:** весь код, автоматические тесты обработки `401`, единственного обновления токена при нескольких параллельных запросах, окончания сессии и очистки локальных данных при выходе; запуск в симуляторе, если он доступен.
- **Заблокировано:** установка на настоящие телефоны, проверка сохранности хранилища после переустановки, письма подтверждения и восстановления пароля на реальном адресе, ссылки возврата при холодном старте. Эти пункты помечаются NOT RUN и **не** засчитываются.

## Задачи

### 1. Каркас приложения (4/01)

- [ ] 1.1 Навигация: `expo-router`, экраны сгруппированы на «до входа» и «после входа».
- [ ] 1.2 Конфигурация окружения: базовый URL API берётся из `EXPO_PUBLIC_*`, а не зашит в код; для разработки — staging.
- [ ] 1.3 Идентификаторы приложения и схема ссылок уже заданы в `app.json`; проверить, что они согласованы с настройками Supabase Auth.

**Проверка:** оба экспорта собираются; `expo-doctor` без замечаний; в бандле нет серверных ключей.

### 2. Сессия и хранилище (4/02)

- [ ] 2.1 Supabase Auth с адаптером хранения на `expo-secure-store`.
- [ ] 2.2 Ошибка записи в хранилище не роняет приложение и не оставляет пользователя в half-signed-in состоянии: она приводит к управляемому выходу.
- [ ] 2.3 Несколько параллельных `401` вызывают **одно** обновление токена, а не по одному на запрос.
- [ ] 2.4 Ошибка обновления токена приводит к управляемому выходу, данные прежнего пользователя очищаются.
- [ ] 2.5 API-клиент получает access token из текущей сессии.

**Проверка:** unit-тесты на все четыре случая с подменённым хранилищем и подменённым сетевым слоем.

### 3. Экраны входа (4/03)

- [ ] 3.1 Вход по email и паролю, регистрация, восстановление пароля, выход.
- [ ] 3.2 Список питомцев после входа — через общий API-клиент, а не прямыми запросами к Supabase.
- [ ] 3.3 Неверный пароль и просроченная ссылка дают понятную ошибку и **не** создают сессию.

**Проверка:** сценарий вход → питомцы → выход в тестах; ошибки провайдера отображаются, а не проглатываются.

### 4. Ссылки возврата (4/04)

- [ ] 4.1 Обработка ссылки подтверждения почты и восстановления пароля.
- [ ] 4.2 Произвольный адрес перенаправления не принимается.
- [ ] 4.3 Повторный и просроченный callback не создают сессию.

**Проверка:** unit-тесты разбора ссылки; проверка на устройстве — NOT RUN.

## Порядок

1 → 2 → 3 → 4. Каждая задача — отдельный коммит.

## Что этот этап не делает

Не добавляет вход через Google, Яндекс и Apple (этап 5), не создаёт анализ и работу с фото (этап 6), не переносит визуальный стиль и полный набор экранов (этап 7).
