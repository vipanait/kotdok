# Исполнимый план этапа 1 — контракт и отделение сервисов

Источник требований: [дорожная карта](../../mobile-api-plan.md), раздел «Этап 1». Отчёт: `docs/verification/stage-1.md`.

База: коммит `0b66430`, ветка `stage-0-baseline`.

Этап делится на два вида работы, и их нельзя смешивать в одном коммите:

- **Новое поведение** (контракты, модель состояния аккаунта, API-клиент) — сначала тест ожидаемой ошибки, затем реализация.
- **Механический перенос** (разделение HTTP и бизнес-логики, перевод старых маршрутов на общие сервисы) — приёмкой служат существующие тесты и сравнение внешнего поведения. Искусственные тесты, повторяющие структуру папок, не пишем.

## Что уже известно про код

- `src/server/symptom-check/symptom-check-service.ts` — 399 строк, где в одной функции `handleSymptomCheckRequest` совмещены разбор `multipart/form-data`, авторизация по cookies, проверка баланса, RAG-поиск, вызов OpenAI, сохранение результата и компенсация кредита. Возвращает `NextResponse`.
- `src/server/dashboard/load-dashboard.ts` вызывает `redirect('/login')` внутри загрузки данных и импортирует тип результата из UI-компонента.
- `src/server/symptom-check/map-symptom-check.ts` импортирует `SymptomCheckRecord` из `@/features/symptom-check/CheckResultContent` — контракт живёт в компоненте экрана.
- `src/server/pets/pet-service.ts` уже почти свободен от HTTP: принимает клиент Supabase и `userId`. Но возвращает объекты Supabase `{ data, error }`, а не обычные данные.
- `src/server/auth/get-auth-user.ts` завязан на `cookies()`.
- `src/shared/types/index.ts` содержит `Profile` без `locale`, хотя колонка есть в БД.

## Задачи

### 1. Контракты как единственный источник (1/02, 1/05)

- [ ] 1.1 Добавить `zod` в `packages/contracts`. Версия уже есть в дереве транзитивно — проверить, что lockfile не тянет новую мажорную.
- [ ] 1.2 Описать в `packages/contracts/src/` схемы: публичный профиль `/me`, питомец, вход создания и изменения питомца, запись истории проверки, страница истории с курсором, статус дополнительной проверки, обратная связь, конверт ошибки, коды ошибок.
- [ ] 1.3 `/me` отдаёт минимальный публичный профиль: id, locale, role, credits, флаги возможностей. Ни `Supabase User`, ни полные строки БД, ни токены наружу не выходят.
- [ ] 1.4 Тесты: заведомо неверный запрос отклоняется схемой, заведомо неверный ответ отклоняется схемой, ответ `/me` не содержит служебных полей Supabase.
- [ ] 1.5 Перенести `SymptomCheckRecord` из UI-компонента в контракты; `map-symptom-check.ts` и компоненты импортируют из пакета.

**Проверка:** `npm run test --workspace @lapka/web` и `npm run typecheck --workspaces` проходят; тест на `/me` перечисляет разрешённые ключи и падает при добавлении лишнего.

### 2. OpenAPI, порождённый из контрактов (1/01, 1/02)

- [ ] 2.1 Скрипт генерации `docs/api/openapi.yaml` из схем контрактов. Zod 4 умеет отдавать JSON Schema без дополнительной зависимости.
- [ ] 2.2 Каждый маршрут раздела 3 дорожной карты получает security, запрос, успешный ответ и применимые ошибки; примеры проходят собственные схемы.
- [ ] 2.3 Команда проверки: повторная генерация не даёт diff; документ принимается валидатором OpenAPI.
- [ ] 2.4 Тест: добавленное несовместимое поле обнаруживается проверкой.

**Проверка:** `npm run openapi:check` exit 0 на неизменённом дереве и ненулевой код после ручной правки схемы без регенерации.

### 3. Модель состояния аккаунта (1/03)

- [ ] 3.1 Миграция: `profiles.status` со значениями `active` и `deleting`, значение по умолчанию `active`, ограничение на набор значений.
- [ ] 3.2 Запретить изменение статуса пользовательским токеном: RLS не должна позволять `update` этой колонки ролям `anon` и `authenticated`.
- [ ] 3.3 Общий guard в сервисном слое: отсутствующий аккаунт и аккаунт в состоянии `deleting` отклоняются до обращения к бизнес-данным.
- [ ] 3.4 Интеграционные тесты на реальной БД: `active` допускается, `deleting` и отсутствующий аккаунт отклоняются, пользовательский токен не может сменить статус.

**Проверка:** `npm run test:integration --workspace @lapka/web` покрывает три случая guard и попытку смены статуса пользовательским токеном.

### 4. Разделение HTTP и бизнес-логики (1/06)

- [ ] 4.1 Вынести из `handleSymptomCheckRequest` бизнес-сервис, принимающий проверенный контекст пользователя и разобранные входные данные и возвращающий обычные данные или типизированную ошибку. HTTP-обработчик остаётся адаптером: разбор запроса, коды статусов, `NextResponse`.
- [ ] 4.2 Отделить загрузку данных кабинета и истории от серверного рендеринга: `loadDashboard` перестаёт вызывать `redirect`, решение о перенаправлении принимает страница.
- [ ] 4.3 `pet-service` возвращает обычные данные и типизированные ошибки вместо объектов Supabase.
- [ ] 4.4 Проверка импортов: в сервисах нет `NextResponse`, `redirect`, `cookies` и импортов из `@/features` и `@/app`.

**Проверка:** сервисы вызываются из тестов без HTTP и cookies; автоматическая проверка импортов падает при возврате запрещённой зависимости.

### 5. Старые веб-маршруты на общих сервисах (1/07)

- [ ] 5.1 Перевести существующие маршруты на общие сервисы, не меняя их внешнего поведения: те же статусы, те же тела ответов, тот же CSRF.
- [ ] 5.2 Регрессионные тесты сравнивают статусы и ответы до и после.

**Проверка:** существующие тесты маршрутов проходят без изменения ожиданий; там, где ожидания меняются, изменение объясняется в отчёте.

### 6. Модель задач, загрузок и удаления (1/04)

- [ ] 6.1 Документ `docs/architecture/jobs-uploads-deletion.md`: состояния, переходы, FK, числовые лимиты и TTL, число повторов, runtime worker, сроки хранения.
- [ ] 6.2 Каждому переходу сопоставлен конкретный тест, который будет написан на этапе 6 или 8.
- [ ] 6.3 Отсутствующий выбор инфраструктуры отмечается блокером реализации подсистемы, а не додумывается.

**Проверка:** документ полон и воспроизводим; выбор runtime worker явно отмечен как заблокированный пунктом 0/06, пока хостинг не проверен.

## Порядок

1 → 2 → 3 → 4 → 5 → 6. Каждая задача — отдельный коммит.

## Что этот этап не делает

Не добавляет маршруты `/api/v1` (этапы 2 и 3), не реализует загрузку фото и очередь задач (этап 6), не реализует очистку данных при удалении аккаунта (этап 8), не трогает мобильные экраны (этап 4).
