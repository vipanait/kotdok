# Исполнимый план этапа 3 — профиль, питомцы, история и баланс

Источник требований: [дорожная карта](../../mobile-api-plan.md), раздел «Этап 3». Отчёт: `docs/verification/stage-3.md`.

База: коммит `dc370f2`, ветка `stage-0-baseline`.

Этап добавляет продуктовые маршруты `/api/v1` поверх слоя авторизации этапа 2 и общих сервисов этапа 1. Новых бизнес-правил не вводит: сайт и API должны работать с одними данными и одинаковой семантикой удаления.

## Что уже есть

- Авторизация по Bearer, конверт ответа с `request_id`, `Cache-Control: private, no-store`, ограничения частоты — этап 2.
- `/api/v1/health` и `/api/v1/me` (GET и PATCH) — этап 2.
- Сервисы питомцев, обратной связи и дополнительной проверки принимают проверенный user id и возвращают обычные данные — этап 1.
- Контракты `PetSchema`, `PetCreateInputSchema`, `PetUpdateInputSchema`, `SymptomCheckRecordSchema`, `CheckHistoryPageSchema`, `ExtraCheckRequestStatusSchema`, `FeedbackInputSchema` и OpenAPI — этап 1.
- Фикстуры содержат две проверки владельца A с **одинаковым** `created_at` — ровно тот случай, который ломает пагинацию по времени.

## Задачи

### 1. Питомцы (3/01)

- [ ] 1.1 `GET /api/v1/pets` — свои питомцы, мягко удалённые скрыты.
- [ ] 1.2 `POST /api/v1/pets` — вход по `PetCreateInputSchema`; `user_id` и `id` из тела отвергаются схемой.
- [ ] 1.3 `GET /api/v1/pets/{id}` — свой питомец; чужой и несуществующий дают `404`, а не `403`.
- [ ] 1.4 `PATCH /api/v1/pets/{id}` — частичное изменение; пустое тело даёт `400`.
- [ ] 1.5 `DELETE /api/v1/pets/{id}` — мягкое удаление, та же семантика, что на сайте: скрываются и связанные проверки.
- [ ] 1.6 Каждый ответ парсится контрактом перед отправкой.

**Проверка:** полный цикл создания, чтения, изменения и удаления на реальной БД; пустой список; неверный и чужой ID; после удаления питомец исчезает из списка, а его проверки — из истории.

### 2. История проверок (3/02)

- [ ] 2.1 `GET /api/v1/checks` — курсорная пагинация по `(created_at, id)`, а не по одному времени.
- [ ] 2.2 Фильтр по питомцу; ограничение размера страницы; запрошенный размер сверх максимума отклоняется, а не молча урезается.
- [ ] 2.3 Мягко удалённые записи и чужие записи не возвращаются.
- [ ] 2.4 `GET /api/v1/checks/{id}` — сохранённый результат, включая старую историю.

**Проверка:** на фикстуре с одинаковыми датами последовательные страницы возвращают каждую запись ровно один раз и не теряют ни одной; чужая запись даёт `404`.

### 3. Баланс только для чтения (3/01)

- [ ] 3.1 Баланс отдаётся в `/me` и нигде не принимается на запись.
- [ ] 3.2 Попытка записать баланс любым путём отклоняется.
- [ ] 3.3 Баланс, который видит сайт, и баланс из API совпадают.

**Проверка:** сравнение значения из `loadDashboard` и из `/api/v1/me` для одного пользователя на одной фикстуре.

### 4. Дополнительная проверка и обратная связь (3/03)

- [ ] 4.1 `GET /api/v1/credits/extra-request` — текущий статус.
- [ ] 4.2 `POST /api/v1/credits/extra-request` — переиспользует существующий сервис; повтор не создаёт вторую pending-заявку.
- [ ] 4.3 `POST /api/v1/feedback` — переиспользует существующий сервис; ошибка сохранения не выдаётся за успех.
- [ ] 4.4 Повторное Telegram-подтверждение начисляет ровно один кредит.

**Проверка:** на реальной БД — повтор заявки даёт конфликт, повторное разрешение заявки не начисляет второй кредит.

### 5. Контракт и документ

- [ ] 5.1 Все ответы соответствуют `docs/api/openapi.yaml`; документ не расходится со схемами.
- [ ] 5.2 Ошибки используют коды контракта, а не текст сообщения.

**Проверка:** существующий тест сверки OpenAPI; ответы маршрутов парсятся схемами в тестах.

## Порядок

1 → 2 → 3 → 4 → 5. Каждая задача — отдельный коммит.

## Что этот этап не делает

Не создаёт анализ через `/api/v1` (этап 6: там появляются задачи, загрузки и идемпотентность), не трогает мобильные экраны (этап 4), не меняет старые веб-маршруты.
