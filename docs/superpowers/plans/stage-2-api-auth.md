# Исполнимый план этапа 2 — авторизация API и изоляция пользователей

Источник требований: [дорожная карта](../../mobile-api-plan.md), раздел «Этап 2». Отчёт: `docs/verification/stage-2.md`.

База: коммит `96025f7`, ветка `stage-0-baseline`.

Этап создаёт слой авторизации `/api/v1` и проверяет изоляцию пользователей **на реальной БД**, а не на моках. Продуктовые маршруты появляются на этапе 3; здесь реализуются только `/health` и `/me` — минимальная поверхность, на которой авторизацию можно проверить.

## Что уже есть

- `profiles.status` (`active`/`deleting`) и общий guard `loadAccount` — этап 1.
- Прямая запись в таблицы пользовательским токеном отозвана, политики сужены до `select` — этап 1. Часть приёмки 2/03 и 2/04 уже покрыта интеграционными тестами `account-status.test.ts`.
- Контракты `PublicProfileSchema`, `ApiErrorEnvelopeSchema`, `ERROR_STATUS`, коды ошибок — этап 1.
- Старые веб-маршруты сохраняют cookies и CSRF; сервисы принимают проверенный user id.

## Задачи

### 1. Проверка Bearer-токена (2/01)

- [ ] 1.1 `src/server/api/bearer-auth.ts`: извлечь Bearer из заголовка, проверить токен через Supabase, вернуть проверенный user id. Cookies не читаются никогда.
- [ ] 1.2 Некорректный Bearer завершается отказом и **не** приводит к попытке авторизоваться через cookies.
- [ ] 1.3 После проверки токена — общий guard `loadAccount`: отсутствующий и `deleting` аккаунт отклоняются до обращения к бизнес-данным.
- [ ] 1.4 Тесты: отсутствующий, испорченный, истёкший, чужого проекта и токен `deleting`-пользователя. Реальные токены получаются входом фикстуры на локальном стенде.

**Проверка:** интеграционные тесты на реальном Supabase; отказ происходит до чтения бизнес-таблиц.

### 2. Конверт ответа и `request_id` (2/06, частично)

- [ ] 2.1 `src/server/api/response.ts`: успешные ответы и ошибки в формате контракта, `request_id` в теле и в заголовке.
- [ ] 2.2 В ответах и журналах нет секретов, фото и текста симптомов.
- [ ] 2.3 Частные ответы не попадают в общий кеш: `Cache-Control: private, no-store`.

**Проверка:** тест формата ошибки против `ApiErrorEnvelopeSchema`; тест заголовков.

### 3. Общий контекст пользователя (2/02)

- [ ] 3.1 `withApiAuth` — обёртка маршрута, отдающая обработчику проверенный контекст: user id, роль, локаль, баланс, состояние.
- [ ] 3.2 `user_id` из тела запроса не меняет владельца — тело вообще не участвует в определении владельца.
- [ ] 3.3 Административная операция запрещена обычному пользователю.
- [ ] 3.4 Чужой объект возвращает `404`, а не `403`.

**Проверка:** матрица A/B/admin на реальной БД.

### 4. Маршруты `/api/v1/health` и `/api/v1/me` (2/01)

- [ ] 4.1 `/health` — публичный, без секретов и без подробностей о БД.
- [ ] 4.2 `/me` — минимальный публичный профиль по контракту, без полей Supabase и токенов.
- [ ] 4.3 Ответ `/me` валидируется схемой контракта перед отправкой.

**Проверка:** тест перечисляет разрешённые ключи; лишнее поле роняет проверку.

### 5. CSRF и разделение путей (2/05)

- [ ] 5.1 CSRF старых веб-маршрутов сохраняется; глобально не отключается.
- [ ] 5.2 Валидный Bearer работает без cookies.
- [ ] 5.3 Неверный Bearer вместе с валидной cookie доступа не получает.
- [ ] 5.4 CORS не используется вместо авторизации.

**Проверка:** прежние CSRF-тесты плюс новые на сочетание Bearer и cookies.

### 6. Ограничения частоты (2/06)

- [ ] 6.1 Распределённый лимит на общем PostgreSQL: два экземпляра сервера расходуют общий счётчик. Redis и брокер не добавляются.
- [ ] 6.2 Лимит применяется к дорогим и чувствительным операциям; запрос сверх лимита даёт `429` **до** запуска AI.
- [ ] 6.3 Числовые лимиты фиксируются здесь и попадают в отчёт.

**Проверка:** интеграционный тест с двумя независимыми клиентами против одной БД; проверяются значения ниже, на границе и выше лимита.

### 7. Состояние аккаунта во всех путях доступа (2/04)

- [ ] 7.1 Проверка состояния действует и на старые веб-сервисы — уже сделано на этапе 1, подтвердить тестом.
- [ ] 7.2 После перевода фикстуры в `deleting` старый JWT не читает и не меняет данные через v1, веб-адаптер и существующие RLS-пути.
- [ ] 7.3 Storage-политики: на этапе 2 проверяются существующие ресурсы; политики новых задач и фото добавляются вместе с ними на этапе 6.

**Проверка:** интеграционный тест повторяет запросы старым токеном после `deleting`.

## Порядок

1 → 2 → 3 → 4 → 5 → 7 → 6. Каждая задача — отдельный коммит.

## Что этот этап не делает

Не реализует продуктовые маршруты питомцев, истории и баланса (этап 3), не добавляет загрузку фото и задачи (этап 6), не трогает мобильные экраны (этап 4).
