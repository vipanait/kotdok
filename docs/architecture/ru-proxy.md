# Прокси для пользователей из России

Сайт и API работают на Vercel, но часть российских сетей не пропускает HTTPS до адресов Vercel. Перед Vercel стоит машина в Selectel с nginx: `lapka.my` указывает на неё, она передаёт каждый запрос в Vercel с исходным доменом. Деплой, превью, cron и переменные окружения остаются на Vercel.

Статус на 19 октября 2026: `lapka.my` и `www.lapka.my` указывают на машину в Selectel, весь трафик идёт через неё. Сертификат Let's Encrypt выпущен до 17 января 2027, продлевается таймером certbot.

До 15 октября 2026 прокси стоял в Yandex Cloud. 15 октября у Yandex Cloud отказали зоны доступности, машина перестала отвечать на всех портах, и сайт с приложением лежали у всех пользователей. DNS вернули на Vercel, а прокси перенесли в Selectel. Замеры ниже сделаны ещё с машины в Yandex Cloud.

Файлы: [`infra/ru-proxy/`](../../infra/ru-proxy/) — конфиг nginx и два скрипта для сервера.

## Почему

Измерено 26 сентября 2026 через check-host.net (узлы Москва ×2, Санкт-Петербург) и с тестовой машины в Yandex Cloud.

| Откуда → куда | Результат |
| --- | --- |
| Германия → `lapka.my` | всегда 200 |
| Москва (ru1) → `lapka.my` | около 7 из 10 запросов висят 15–25 с и обрываются |
| Москва (ru2), Петербург → `lapka.my` | почти всегда 200 |
| Москва → `kotdok.vercel.app` | висит на обоих московских узлах |
| Все узлы → Supabase | отвечает |
| Все узлы → адреса Vercel по HTTP (порт 80) | отвечает |
| Yandex Cloud → `lapka.my` через `216.198.79.1`, `64.29.17.1`, `76.76.21.21` | 75 из 75 |
| Yandex Cloud → `kotdok.vercel.app` (`…131`) | 8 из 50, TCP не устанавливается |
| Все узлы → машина в Yandex Cloud | TCP 4–14 мс, включая ru1 |

TCP до Vercel устанавливается, HTTPS зависает — это фильтрация у провайдера, а не сбой сервера. Какие адреса Vercel недоступны, зависит от сети. Cloudflare у домена только DNS и к проблеме отношения не имеет.

## Схема

```
браузер, приложение ──► lapka.my, www.lapka.my ──► машина в Selectel (nginx)
                                                      │  Host и SNI: исходный домен
                                                      ▼
                                   216.198.79.1 / 64.29.17.1 / резерв 76.76.21.21 (Vercel)
```

- Проксируется только `lapka.my` и `www.lapka.my`. Запрос к другому домену отклоняется, иначе машина стала бы прокси ко всем сайтам на Vercel.
- В Vercel идут адреса для собственных доменов, **не** `*.vercel.app`: из российских облаков до последних соединение не устанавливается.
- Сертификат Vercel проверяется (`proxy_ssl_verify on`).
- Ответы не буферизуются: страницы Next.js приходят потоком.
- `/.well-known/acme-challenge/` отвечает сама машина, если файл её, иначе передаёт в Vercel. Так сертификаты продлевают и машина, и Vercel.

**Мимо прокси:** Supabase (вход, загрузка фото — браузер и приложение ходят туда напрямую) и cron Vercel (вызывается внутри Vercel). Приложение не определяет пользователя по IP, поэтому то, что Vercel видит IP машины, ничего не ломает.

## Установка

```bash
scp infra/ru-proxy/lapka.conf root@<IP>:/tmp/
ssh root@<IP> 'bash -s' < infra/ru-proxy/install.sh
```

Скрипт ставит nginx и certbot, кладёт конфиг и временный самоподписанный сертификат. Повторный запуск безопасен: выпущенный сертификат не трогается. Чтобы обновить конфиг, те же две команды.

## Проверка до переключения DNS

С любой машины, подставив IP. `-k` — потому что сертификат пока самоподписанный.

```bash
curl -sk -o /dev/null -w "%{http_code}\n" --resolve lapka.my:443:<IP> https://lapka.my/
curl -sk --resolve lapka.my:443:<IP> https://lapka.my/api/v1/health
curl -sk -o /dev/null -w "%{http_code}\n" --resolve lapka.my:443:<IP> https://lapka.my/api/v1/me
```

Ожидается `200`, `{"status":"ok"}` и `401`.

## Переключение DNS

DNS домена — **Cloudflare** (NS `nick.ns.cloudflare.com`, `sierra.ns.cloudflare.com`). SendPulse здесь только отправляет почту, от него в зоне одна SPF-запись; её и MX (`smtp.google.com`) не трогать.

Cloudflare → `lapka.my` → DNS → Records:

| Запись | Было | Стало |
| --- | --- | --- |
| `lapka.my` (`@`) | A `216.198.79.1` | A `<IP машины>`, **DNS only** (серое облако), TTL Auto |
| `www` | CNAME `093fe1e0afef66e1.vercel-dns-017.com` | A `<IP машины>`, **DNS only**, TTL Auto |

Оранжевое облако (проксирование Cloudflare) не включать: адреса Cloudflare в России тоже ограничивают.

Сразу после смены записей выпустить сертификат:

```bash
ssh root@<IP> 'bash -s' < infra/ru-proxy/issue-cert.sh
```

Пока он не выпущен, у тех, кого DNS уже направил на машину, браузер предупреждает о сертификате. Обычно это одна-две минуты.

## Мимо прокси: вебхук Телеграма

Кнопки «Подтвердить» и «Отклонить» в канале заявок вызывают вебхук бота, и вызывает его сервер Телеграма, а не человек из России. Прокси ему не нужен: вебхук указывает прямо на Vercel, `https://kotdok.vercel.app/api/telegram/webhook`, а не на `lapka.my`.

Почему: после переключения DNS вебхук остался на `lapka.my`, а серверы Телеграма до машины в Yandex Cloud не достучались. 7 октября 2026 после нажатия кнопки `getWebhookInfo` показал `last_error_message: Connection timed out` и одно событие в очереди, в логах Vercel запроса не было. С обычных адресов `lapka.my` при этом отвечал, поэтому со стороны казалось, что всё работает. Заявка от 3 октября висела в `pending`, пока вебхук не переставили на Vercel.

Переменные `TELEGRAM_*` в Vercel помечены как Sensitive: их значение не отдаёт ни `env pull`, ни панель. Поэтому, чтобы переставить вебхук, секрет задаётся заново. Команды из корня репозитория, секрет лежит в файле и на экран не выводится:

```bash
umask 077; openssl rand -hex 32 | tr -d '\n' > ~/.lapka-tg-secret
vercel env update TELEGRAM_WEBHOOK_SECRET production --sensitive --yes < ~/.lapka-tg-secret
vercel redeploy kotdok.vercel.app --target production
# ждём 200, а не 403
curl -s -o /dev/null -w '%{http_code}\n' -X POST https://kotdok.vercel.app/api/telegram/webhook \
  -H 'Content-Type: application/json' -H "X-Telegram-Bot-Api-Secret-Token: $(cat ~/.lapka-tg-secret)" -d '{}'
curl -s -X POST "https://api.telegram.org/bot$(grep '^TELEGRAM_BOT_TOKEN=' apps/web/.env.staging.local | cut -d= -f2-)/setWebhook" \
  -d url=https://kotdok.vercel.app/api/telegram/webhook -d secret_token="$(cat ~/.lapka-tg-secret)"
```

Токен в `apps/web/.env.staging.local` — продового бота: стейджинг шлёт заявки тем же ботом в тот же канал, а вебхук у бота один и смотрит на прод. Поэтому кнопки на заявках со стейджинга ничего не делают.

После этого нажать кнопку на висящей заявке ещё раз и проверить `getWebhookInfo`: `url` на `kotdok.vercel.app`, `last_error_message` пустой.

## Риски и что проверять

- **Сертификат Vercel.** Прокси проверяет его, поэтому если Vercel не продлит сертификат `lapka.my`, сайт начнёт отдавать `502`. Продление идёт через проброс `/.well-known/acme-challenge/`, но на практике ещё не проверялось. Текущий истекает **1 декабря 2026**, продление ожидается в начале ноября. Проверка с машины:
  ```bash
  echo | openssl s_client -connect 216.198.79.1:443 -servername lapka.my 2>/dev/null | openssl x509 -noout -enddate
  ```
- **Адреса Vercel записаны в конфиге.** Если Vercel их сменит, нужно поправить `upstream` в `lapka.conf`. Актуальные адреса — в настройках домена в Vercel.
- **Размер заголовков.** Сессия Supabase лежит в cookie кусками по ~3 КБ, и ответ на вход ставит их все сразу. С настройками nginx по умолчанию (4 КБ на заголовки ответа) вход заканчивался `502` на `/auth/callback` (5 октября 2026). Поэтому в конфиге буферы по 32 КБ. Проверка: длинный `next` раздувает заголовок `Location`. Ожидается `307`, а не `502`:
  ```bash
  curl -s -o /dev/null -w "%{http_code}\n" "https://lapka.my/auth/callback?code=x&next=%2F%3Fp%3D$(printf 'a%.0s' $(seq 1 8000))"
  ```
- **Одна машина.** Упала машина — сайт недоступен для всех, не только для России. Лечится откатом DNS.
- **Проверка Vercel для IP прокси.** Весь трафик приходит в Vercel с одного адреса, и автоматическая защита Vercel от DDoS начинает отвечать ему `403` со страницей Security Checkpoint (8 октября 2026). Браузер её проходит, приложение нет и пишет «Нет связи». Поэтому у проекта есть правило обхода для IP прокси, оно доступно только на тарифе Pro. При смене машины правило добавляется заново:
  ```bash
  printf '%s' '{"projectScope":true,"sourceIp":"<IP>","note":"ru-proxy"}' | vercel api -X POST --input - "/v1/security/firewall/bypass?projectId=prj_07jOV73R0hWuHG2I9agVjzLS1SDv&teamId=team_SEMA5Ou4Y9xl7NGLDh0vwiZd"
  ```
  Правило для `90.156.157.146` добавлено 19 октября 2026. Правило для старого адреса Yandex `51.250.0.247` пока не удалено.
- **TLS расшифровывается в Selectel.** Провайдер технически имеет доступ к трафику, включая данные о питомцах и токены входа.
- **Supabase не проксируется.** Сейчас доступен из всех проверенных сетей. Если его начнут ограничивать — отдельная задача: смена адреса Supabase разлогинит пользователей и потребует обновления приложения.
