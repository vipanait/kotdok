# Модель задач анализа, загрузок и удаления аккаунта

Документ ведётся по пункту **1/04** дорожной карты. Он фиксирует состояния, переходы, внешние ключи, числовые лимиты, повторы и сроки хранения **до** реализации подсистем на этапах 6, 8 и 9. Значения, которые нельзя выбрать без внешнего подтверждения, помечены как блокеры, а не додуманы.

Схемы запросов и ответов, на которые ссылается документ, лежат в `packages/contracts/src/analysis.ts` и `deletion.ts` и уже опубликованы в `docs/api/openapi.yaml`.

## 1. Общие решения

- Идентификаторы разделены: `job_id` обозначает обработку, `check_id` — сохранённый результат. Незавершённая или неуспешная задача не создаёт запись в истории.
- Клиент сохраняет ключ идемпотентности **до** отправки и `job_id` после ответа. Потерянный ответ восстанавливается повтором того же запроса с тем же ключом.
- Все денежные операции и удаление блокируют и проверяют одну согласованную запись аккаунта, чтобы исключить гонки.
- Ни одна из новых таблиц не даёт прав записи ролям `anon` и `authenticated`: миграция `20260906000000` отзывает их и меняет default privileges, поэтому новая таблица наследует запрет автоматически.

## 2. Задача анализа

### Состояния и переходы

| Из | В | Когда |
| --- | --- | --- |
| — | `queued` | Транзакция создания: аккаунт `active`, питомец и загрузки принадлежат пользователю, кредит зарезервирован |
| `queued` | `processing` | Worker атомарно захватил задачу и получил lease |
| `processing` | `completed` | Результат сохранён, ledger связан с `check_id`, финальное состояние — в одной транзакции |
| `processing` | `failed` | Исчерпаны попытки либо ответ модели окончательно непригоден; возврат кредита — в той же транзакции |
| `processing` | `queued` | Lease истёк, задача восстановлена; счётчик попыток увеличен |

Завершить задачу может только актуальный владелец lease. Запоздалый worker не перезаписывает результат нового обработчика.

### Ключи и внешние ключи

- Уникальность `(user_id, idempotency_key)` — повтор с тем же ключом и теми же данными возвращает прежний `job_id`.
- Отпечаток нормализованных входных данных хранится рядом с задачей; тот же ключ с другими данными даёт `409 conflict`.
- `user_id` → `auth.users(id)`. Действие при удалении выбирается вместе с пунктом 8/02: задача очистки и квитанция статуса **не** удаляются каскадно вместе с Auth, иначе нечем подтверждать завершение.
- `check_id` → `symptom_checks(id)`, заполняется только при успехе.
- Ledger-запись резервирования связывается с `check_id` после сохранения результата.

### Числовые значения

| Параметр | Значение | Основание |
| --- | --- | --- |
| Размер `Idempotency-Key` | 8–200 символов | зафиксировано в контракте |
| Длина описания симптомов | 3–2000 символов | текущее поведение маршрута |
| Число фото на задачу | не более 5 | текущее поведение маршрута |
| Размер одного фото | не более 5 МБ | текущее поведение маршрута |
| Таймаут вызова AI | не более 240 с | лимит выполнения функции на Hobby — 300 с; оставляем запас на сохранение результата |
| Длительность lease | 360 с | превышает и таймаут AI, и предельное время жизни функции, поэтому убитый платформой worker не удерживает задачу |
| Число попыток | **БЛОКЕР** | зависит от бюджета на AI, решение владельца |
| Период запуска worker | **БЛОКЕР** | на Hobby cron Vercel даёт лишь один запуск в сутки; нужен другой планировщик, см. ниже |

Гарантия: однократное пользовательское списание и однократное сохранение результата. Однократность внешнего вызова AI при любом сбое **не** обещается.

### Runtime worker — что известно и что осталось выбрать

Базовое решение — таблица задач в существующем PostgreSQL с атомарным захватом; Redis, отдельный брокер и Kubernetes в MVP не добавляются.

Хостинг: Vercel, тариф **Hobby**. Измеренные лимиты — в [deployment.md](deployment.md).

**Времени достаточно.** Функция живёт до 300 секунд, чего с запасом хватает на вызов модели и сохранение результата. Ранее этот пункт был помечен как блокирующий по времени выполнения — это оказалось неверно.

**Не хватает планировщика.** Cron на Hobby запускается не чаще раза в сутки и с точностью ±59 минут; более частое выражение вообще роняет деплой. Очередь, которую опрашивают раз в день, бесполезна. Варианты, между которыми нужно выбрать:

| Вариант | Что даёт | Чего стоит |
| --- | --- | --- |
| Тариф Pro на Vercel | cron раз в минуту с поминутной точностью, 800 с выполнения | платный |
| `pg_cron` и `pg_net` в самой Supabase | планировщик рядом с очередью, вызов worker-эндпоинта по HTTP из базы | требует включения расширений; расписание живёт в БД, а не в репозитории |
| Внешний планировщик, например расписание GitHub Actions | бесплатно на текущих тарифах | минимальный интервал около 5 минут, срабатывание негарантированное |
| Обработка в том же запросе, без очереди | ничего не нужно планировать | противоречит решению дорожной карты: результат теряется при разрыве связи, а повтор списывает кредит заново |

Пробная задача не запускалась ни в одном из вариантов. Само наличие таблицы задач не означает наличия работающего потребителя.

## 3. Загрузки фотографий

### Состояния

| Состояние | Значение |
| --- | --- |
| `granted` | Выдано ограниченное разрешение на запись одного объекта |
| `uploaded` | Объект записан, размер и фактический формат подтверждены сервером |
| `attached` | Загрузка привязана к задаче анализа |
| `expired` | Срок разрешения истёк без записи |

### Правила

- **Загрузка через сервер невозможна.** Vercel обрывает любое тело крупнее 4.5 МБ до вызова функции, а приложение объявляет до пяти файлов по 5 МБ. Измерено на production: 1 МБ доходит до приложения, 5 МБ получает `413` от платформы. Поэтому фото идут напрямую в приватное хранилище, а сервер получает только идентификаторы. Это условие работоспособности, а не предпочтение в архитектуре.
- Сервер выдаёт `upload_id`, привязанный к владельцу и **неизменяемому** объекту. Анализ принимает только эти идентификаторы; произвольный URL для серверной загрузки не принимается никогда.
- Повторная подмена объекта после проверки запрещена.
- Незавершённая или просроченная загрузка не резервирует кредит.
- Проверяется не только заявленный MIME, но и фактический формат, а также предел разрешения изображения в пикселях.
- Анонимное чтение объекта запрещено.
- Очистка не удаляет файлы активной задачи до её завершения или предельного срока.

### Числовые значения

| Параметр | Значение | Основание |
| --- | --- | --- |
| Допустимые типы | `image/jpeg`, `image/png`, `image/webp`, `image/heic`, `image/heif` | контракт `UPLOAD_CONTENT_TYPES` |
| Файлов за один запрос | 1–5 | контракт |
| Срок действия разрешения на запись | **БЛОКЕР** | согласуется с лимитами хранилища |
| Размер тела запроса к серверу | 4.5 МБ, жёстко | лимит платформы; именно поэтому фото не могут идти через сервер |
| Предел разрешения изображения | **БЛОКЕР** | зависит от лимитов AI-провайдера |
| TTL брошенной загрузки | **БЛОКЕР** | согласуется со сроком хранения исходников |
| Срок хранения исходников после анализа | **БЛОКЕР** | требует решения владельца о приватности |
| TTL выданного signed URL | **БЛОКЕР** | политики доступа не отзывают уже выданный URL мгновенно, поэтому срок минимизируется |

Постоянная фотогалерея в MVP не входит: хранение временное и служит только тому, чтобы обработчик мог продолжить анализ после завершения HTTP-запроса.

## 4. Удаление аккаунта

### Состояния аккаунта

Реализовано на этапе 1: `profiles.status` — `active` или `deleting`, значение по умолчанию `active`, изменение доступно только доверенному серверу. Пользовательский токен не имеет прав записи в `profiles`.

### Состояния задачи очистки

| Состояние | Значение |
| --- | --- |
| `pending` | Запрос принят, аккаунт переведён в `deleting`, новые операции запрещены |
| `in_progress` | Выполняется шаг очистки; прогресс сохраняется, чтобы повтор продолжал с сохранённого места |
| `action_required` | Внешний сервис недоступен и требуется вмешательство; **не** выдаётся за успех |
| `completed` | Очистка завершена согласно опубликованной политике |

### Порядок шагов

1. Атомарно: перевести аккаунт в `deleting`, создать задачу очистки, сохранить хеш квитанции. Повтор запроса не создаёт вторую задачу.
2. Остановить и запретить задачи анализа; результаты уже выполняющихся задач не публикуются.
3. Отозвать Apple-токены.
4. Удалить принадлежащие пользователю объекты Storage — **до** окончательного удаления Auth.
5. Удалить связанные данные согласно карте данных этапа 8.
6. Удалить пользователя в Supabase Auth.
7. Отметить задачу `completed`; квитанция остаётся доступной весь опубликованный срок.

### Квитанция статуса

- Клиент создаёт криптографически случайный секрет **до** отправки и хранит его отдельно от сессии; сервер сохраняет только его хеш вместе с задачей в одной транзакции.
- Секрет передаётся в заголовке `X-Deletion-Receipt`, никогда в URL, и не попадает в журналы.
- Ответ содержит только `pending`, `completed` или `action_required` — без email, user ID и содержимого данных; `Cache-Control: no-store`, ограничение частоты.
- Проверка статуса работает после блокировки обычной сессии, но не открывает бизнес-API.

### Внешние ключи и удержание

- `transactions.user_id` и `credit_ledger.user_id` имеют `ON DELETE RESTRICT` — подтверждено интеграционным тестом схемы. Прямое удаление пользователя с такими записями не сработает, поэтому этап 8 выбирает одну схему: удаление допустимых записей либо минимальный отделённый архив.
- Задача очистки и квитанция не удаляются каскадно вместе с Auth: они нужны для повторов и подтверждения завершения. Хранят минимальные служебные данные с ограниченным сроком.

### Числовые значения

| Параметр | Значение | Основание |
| --- | --- | --- |
| Длина секрета квитанции | 32 байта, hex | контракт `DeletionReceiptSecretSchema` |
| Срок жизни квитанции | **БЛОКЕР** | должен покрывать опубликованный срок удаления и период получения подтверждения |
| Опубликованный срок выполнения удаления | **БЛОКЕР** | измеряется пробными удалениями на staging, пункт 9/06 |
| Срок хранения финансовых записей | **БЛОКЕР** | требует определения юрисдикции и обязательств; без этого окончательная очистка финансовых данных блокируется |
| Срок истечения резервных копий | **БЛОКЕР** | не проверены настройки backup Supabase, пункт 0/06 |

## 5. Соответствие переходов тестам

Каждому переходу соответствует конкретная проверка в исполнимом плане этапа, который его реализует. Здесь фиксируется соответствие, сами тесты пишутся вместе с кодом.

| Переход или правило | Проверка | Этап |
| --- | --- | --- |
| Создание задачи при одном кредите, две параллельные | максимум одна принятая задача | 6/05 |
| Десять параллельных одинаковых запросов | один `job_id`, одно списание | 6/04 |
| Тот же ключ, другой payload | `409` | 6/04 |
| Ключи разных пользователей | независимы | 6/04 |
| Перезапуск worker с зависшей задачей | задача восстановлена | 6/05 |
| Истёкший lease, старый worker | результат не зафиксирован | 6/06 |
| Инъекция сбоя на каждом SQL-шаге | нет `completed` без результата и `failed` без компенсации | 6/06 |
| Окончательный сбой | баланс равен исходному, запись возврата одна | 6/07 |
| Перезапись объекта загрузки | отклонена | 6/02 |
| Изображение сверх предела пикселей | отклонено | 6/02 |
| Незавершённая загрузка | кредит не списан | 6/02 |
| Управляемые часы, очистка | активный файл сохранён, просроченный удалён | 6/02 |
| Мягкое удаление питомца во время анализа | новые задачи запрещены, скрытый результат не попадает в историю | 6/10 |
| Параллельные запросы удаления аккаунта | одна задача, одно состояние `deleting` | 8/03 |
| Сбой на каждом шаге очистки | продолжение с сохранённого места, нет ложного `completed` | 8/05 |
| Старые access/refresh токены после удаления | не открывают данные | 8/06 |
| Поздний результат worker, Telegram и платёжный webhook | не создают строк удалённому пользователю | 8/07 |
| Очистка Storage до Auth | нет бесхозных объектов, ранее выданный URL не отдаёт файл | 8/08 |
| Потерянный ответ `202` | сохранённая квитанция возвращает статус без сессии | 9/04 |
| Истёкшая квитанция и чужой секрет | отклонены, данные не раскрыты | 9/04, 9/05 |

## 6. Сводка блокеров

Реализацию соответствующей подсистемы нельзя начинать, пока не закрыт её блокер:

1. **Чем запускать worker** — блокирует этап 6. Времени выполнения хватает (300 с на Hobby), планировщика нет: cron допускает один запуск в сутки. Нужно выбрать между тарифом Pro, `pg_cron` в Supabase и внешним планировщиком.
2. **Сроки хранения фото и TTL загрузок** — блокирует этап 6. Требуется решение владельца о приватности.
3. **Обязательства по хранению финансовых записей** — блокирует окончательную очистку на этапе 8. Требуется определение юрисдикции.
4. **Настройки резервного копирования Supabase** — блокирует пункт 8/09.
5. **Опубликованный срок удаления** — измеряется на staging, которого пока нет (пункт 0/04).
