# План общего API и мобильного приложения «Лапка»

Дата: 6 сентября 2026. Редакция 3: приёмка каждого пункта. Статус: дорожная карта, реализация не начата.

Документ задаёт архитектуру, зависимости и приёмку этапов. Перед каждым этапом готовится небольшой исполнимый план с точными файлами, контрактами и командами проверки по актуальному состоянию репозитория; место хранения — `docs/superpowers/plans/`. Это не инструкция для автономной реализации всех подсистем за один проход. Для исполнения используются `superpowers:executing-plans` либо согласованный процесс `superpowers:subagent-driven-development`. Завершение этапов отмечается чекбоксами в разделе 5.

Цель: один мобильный проект Expo / React Native для iOS и Android, существующий сайт Next.js и общие аккаунты, питомцы, проверки и баланс в Supabase. Обязательные функции релиза: Sign in with Apple и удаление аккаунта.

## 1. Решения по архитектуре

- Развиваем API внутри существующего Next.js. Отдельный новый веб-сервер на старте не нужен. Сложную обработку задач выполняет отдельный worker с надёжным запуском, а не процесс после отправки HTTP-ответа.
- 16.2.3 — обнаруженная версия Next.js, а не требование сохранять её до релиза. На этапе 0 проверяем поддерживаемые версии и security advisories Next.js, React, Node.js и зависимостей. Необходимые исправления безопасности выполняем отдельным изменением до публикации. Переписывание на Go в MVP не входит.
- Мобильный клиент обращается к `/api/v1`. Supabase Auth отвечает за вход и сессии. Бизнес-данные мобильный клиент получает через API; ключи AI, Apple и Supabase service role остаются на сервере.
- Существующие веб-маршруты продолжают работать. Веб и API используют общие сервисы. Серверным страницам не требуется вызывать собственный HTTP API.
- В сервисах нет `cookies()`, `redirect()`, `NextResponse` и зависимости от компонентов экранов. Они получают проверенный контекст пользователя и возвращают обычные данные. HTTP, cookies и обновление страниц остаются в адаптерах Next.js.
- Обычные защищённые маршруты мобильного API принимают только Bearer access token. Старые веб-маршруты сохраняют cookies и CSRF. Некорректный Bearer не должен приводить к попытке авторизоваться через cookies.
- Исключения: публичный health, OAuth callback с проверкой протокола и ограниченный маршрут статуса удаления с отдельной секретной квитанцией. Веб-удаление использует cookie/CSRF-адаптер того же сервиса, а не анонимный вызов мобильного API.
- Общий пакет содержит контракты, схемы валидации, словари и переносимые функции; он не импортирует Next.js, серверные SDK и DOM. UI веба и UI телефона отдельные.
- Используем монорепозиторий с npm workspaces: `apps/web` — Next.js и API, `apps/mobile` — Expo, `packages/contracts` — контракты, `packages/shared` — переносимые функции и переводы. `supabase/migrations` остаётся в корне. Перенос выполняется этапом 0.1 до разработки API; приложения проверяются, собираются и выпускаются независимо.
- Покупки, подписки, push-уведомления и полный офлайн вынесены за пределы первого MVP. Баланс и бесплатные дополнительные проверки входят. Решение владельца: переносим текущие пользовательские функции без покупок; целевое распространение — все страны, доступные для приложения и аккаунта в магазинах. Первый выпуск — тестовый, с аккаунтом физлица.

### Граница MVP и условия выбора инфраструктуры

Обязательный релиз: email/Google/Яндекс/Apple, питомцы, фото-анализ, результат и история, баланс, дополнительная проверка, обратная связь, два языка, удаление из приложения и веба. Первый внутренний прототип ограничен email-входом, питомцем и одной проверкой; он не считается готовым к магазину.

Базовое решение для задач — таблица задач в существующем PostgreSQL с атомарным созданием и захватом задач; Redis, отдельный брокер и Kubernetes для MVP не добавляем. На этапе 0 фиксируем фактический хостинг и возможность запуска worker. На этапе 1 оформляем его deployment-профиль: длительность выполнения, период запуска, параллелизм, таймаут AI, число попыток и процедуру восстановления. Если текущий хостинг не поддерживает нужное выполнение, до этапа 6 выбираем подходящий управляемый runtime и подтверждаем пробной задачей. Само наличие очереди не означает наличие работающего потребителя.

Приватное временное хранение фото — новая инфраструктура, а не уже существующая функция. Оно нужно, чтобы обработчик мог продолжить анализ после завершения HTTP-запроса. На этапе 1 фиксируем квоты и TTL загрузок, хранение и очистку фото, задач и ключей повторных запросов. Эти решения входят в стоимость MVP; постоянная фотогалерея и общий офлайн-кеш результатов не входят.

## 2. Что подтверждено исходниками

- Есть Vitest и тесты API/сервисов; многие зависимости в них заменены моками. Это не подтверждает правильность реальных SQL-транзакций, RLS и OAuth.
- `src/server/auth/get-auth-user.ts` работает с cookies. Кабинет и страница результата читают данные на сервере без отдельного API для мобильного клиента.
- `src/server/symptom-check/symptom-check-service.ts` совмещает HTTP, авторизацию, AI, баланс и сохранение результата; его нужно разделить.
- Тип результата в `map-symptom-check.ts` импортируется из UI-компонента: контракт необходимо вынести в общий пакет.
- Для фотографий сейчас предусмотрено до пяти файлов по 5 МБ. Лимит HTTP-хостинга и поддержка фактических форматов требуют отдельной проверки.
- Удаление питомца сейчас мягкое и скрывает связанные проверки. Удаление аккаунта должно быть самостоятельным процессом очистки данных.
- `transactions.user_id` и `credit_ledger.user_id` имеют `ON DELETE RESTRICT`. Прямое удаление пользователя с такими записями не сработает.
- Покупки отключены; реализованный провайдер тестовый.
- В каталоге миграций не видны определения создания всех исходных таблиц. Восстановление чистой тестовой базы необходимо проверить первым этапом.

Это анализ репозитория, не аудит рабочей базы и настроек облачных сервисов. Тесты при подготовке этого документа не запускались.

## 3. Предварительный контракт API

Маршруты ниже предлагаемые, не реализованные. На этапе 1 фиксируем их в OpenAPI со схемами запросов, ответов и примерами ошибок.

| Метод и маршрут | Назначение |
| --- | --- |
| `GET /api/v1/health` | Безопасная проверка доступности; подробная готовность БД — только для инфраструктуры |
| `GET /api/v1/me` | Профиль, язык, баланс и доступные возможности |
| `PATCH /api/v1/me` | Только разрешённые поля профиля, без изменения баланса/роли |
| `GET /api/v1/pets` | Список своих питомцев |
| `POST /api/v1/pets` | Создать питомца |
| `GET /api/v1/pets/{id}` | Получить своего питомца |
| `PATCH /api/v1/pets/{id}` | Изменить питомца |
| `DELETE /api/v1/pets/{id}` | Сохранить текущую семантику мягкого удаления |
| `POST /api/v1/uploads` | Получить ограниченное разрешение на загрузку фото в приватное хранилище |
| `POST /api/v1/checks` | Создать задачу анализа, вернуть `202`, `job_id` и `status_url` |
| `GET /api/v1/checks` | История с курсорной пагинацией и фильтром по питомцу |
| `GET /api/v1/checks/{id}` | Сохранённый результат по `check_id`, включая старую историю |
| `GET /api/v1/check-jobs/{job_id}` | Состояние задачи и `check_id` после успеха |
| `GET /api/v1/credits/extra-request` | Текущий статус дополнительной проверки |
| `POST /api/v1/credits/extra-request` | Запросить дополнительную проверку |
| `POST /api/v1/feedback` | Отправить обратную связь |
| `POST /api/v1/account-deletion` | После повторного подтверждения личности принять запрос и вернуть `202` |
| `GET /api/v1/account-deletion/status` | Минимальный статус по отдельной секретной квитанции, без доступа к профилю |

Вход, регистрация, обновление сессии и восстановление пароля идут через Supabase Auth; второй самостоятельный сервис паролей не создаём. Для серверного обмена Apple authorization code и отзыва доступа может понадобиться отдельный узкий маршрут — фиксируем после прототипа Apple.

Общие правила: UTC-даты ISO 8601, устойчивые коды ошибок, `request_id`, ограниченный размер страницы, отсутствие стека/секретов в ответах. Формат ошибки: `{ error: { code, message, request_id, details? } }`. Клиент принимает решения по `code`, а не по тексту сообщения. Чужой объект возвращает `404`; неверный токен — `401`; ограничения частоты — `429`. Частные ответы не попадают в общий CDN-кеш. Изменения v1 остаются обратно совместимыми: опубликованное приложение нельзя обновить у всех мгновенно.

Идентификаторы разделены: `job_id` обозначает обработку, `check_id` — сохранённый результат. Незавершённые/ошибочные задачи не подменяют записи истории. Приёмка: старые URL результатов остаются рабочими, новая задача после успеха ведёт к одному результату.

Для создания анализа обязательны `Idempotency-Key` и серверный отпечаток нормализованных входных данных. Повтор с тем же ключом и данными возвращает прежний `job_id`; изменение данных — `409`. Ошибки: `400` — неверный запрос, `402` — недостаточно проверок, `413` — превышен размер, `415` — неподдерживаемый формат, `429` — превышена частота, `503` — временно недоступная зависимость. Автоматический повтор изменения данных разрешён только там, где контракт гарантирует защиту от дубликата.

## 4. Этапы и критерии завершения

Каждый пункт имеет стабильный ID `этап/номер`, чекбокс и собственную приёмку сразу после описания. Чекбокс отмечается только при наличии фактических доказательств, а не после написания кода.

Для каждого ID в отчёте `docs/verification/stage-<номер>.md` фиксируются: ревизия, окружение/ОС/build ID, команда или последовательность ручных действий, ожидаемый и фактический результат, ссылка на безопасный лог/артефакт и статус `PASS`, `FAIL` или `NOT RUN`. Чувствительные значения в отчёт не включаются. Если нет устройства, доступа или выбранного лимита, статус — `NOT RUN`; пункт и этап не считаются принятыми. Независимую работу можно продолжать, не выдавая непроверенную зависимость за готовую.

Числовые TTL, лимиты, число повторов и сроки хранения фиксируются на этапе 1 до тестирования зависимых пунктов. Для границ проверяются значения ниже, на границе и выше лимита; время проверяется управляемыми часами. Документирование решения принимается проверкой полноты и воспроизводимости; оно не заменяет runtime-тест зависимого поведения. Приёмка этапа требует всех его пунктов и общих автоматических/ручных проверок ниже.

## 5. Порядок и рабочий процесс

Порядок выполнения: 0 → 0.1 → 1 → 2 → 3 → 4 → 5 → 8 → 9 → 7 → 10 → 11 → **6**. Изначально этап 6 стоял сразу после пятого; **6 сентября 2026 владелец перенёс его в самый конец** и одновременно отложил Android, чтобы довести приложение для iOS. Загрузка фотографий в продукте отключена (пункт 0.1 открытых вопросов закрыт этим отключением), поэтому перенос ничего не ломает у пользователей — он лишь откладывает возвращение фото. Следствие, о котором стоит помнить: фоновые задачи появляются вместе с этапом 6, значит до самого конца очереди их нет, и всё, что на них опиралось, придётся либо делать без них, либо ждать. Номера сохранены для ссылок. Удаление переносится перед полировкой полного UI, чтобы его блокирующие проблемы не обнаружились в конце. Минимальная модель `active/deleting` реализуется на этапе 1, а реальная очистка — на этапе 8. Этап 3 читает старую историю; фоновые задачи появляются на этапе 6.

### Обязательная история выполнения

После каждого этапа выпускается подробный отчёт по [форме отчёта](verification/REPORT_TEMPLATE.md). Этап не закрывается без отчёта и покрытия всех его ID приёмки. Если работа остановлена или часть проверок недоступна, сохраняется промежуточный отчёт с незавершённым статусом. В ответе пользователю — итог этапа и ссылка на полный отчёт.

- `docs/verification/README.md` — журнал этапов со статусами и ссылками.
- `docs/verification/stage-<номер>.md` — содержание этапа, изменения по файлам, решения и отклонения от плана, таблица приёмки всех ID, результаты автоматических и ручных проверок, дефекты, ограничения и итог.
- `docs/verification/runs/stage-<номер>/<YYYYMMDD-HHMMSSZ>.md` — отдельная запись каждого цикла проверки: ревизия/состояние рабочего дерева, команды, окружение, результаты и ссылки на артефакты. Новый цикл получает новый файл; неуспешные запуски не заменяются успешными.
- Большие логи, скриншоты и видео допускается хранить в CI/хранилище артефактов; отчёт фиксирует ссылку, срок доступности и краткое существенное свидетельство. Истечение CI-артефакта не должно уничтожать единственную запись результата. Секреты и реальные пользовательские данные в отчёты и артефакты не попадают.

Для каждого тестового набора указывать фактические количества passed/failed/skipped, если инструмент их сообщает, exit code и что именно проверяет набор. Процент покрытия указывать только если он измерен, с командой и областью измерения. Пропущенные проверки не считать пройденными. Для ручных проверок записывать предусловия, шаги, ожидаемый/фактический результат, исполнителя, устройство/ОС/build ID и свидетельство; проверку пользователя явно отличать от собственной проверки агента.

История сохраняет и ошибки: что упало, как воспроизвести, что исправлено, какой повтор подтвердил исправление. После изменения кода прежний PASS не доказывает работу новой ревизии: связанные проверки запускаются повторно и получают новую запись. Статус этапа `ACCEPTED` допустим только при PASS всех обязательных критериев и наличии отчёта; иначе `IN_PROGRESS`, `BLOCKED` или `FAILED`. Пока работа не начата — `PLANNED`.

Приёмка отчётности: все ID этапа представлены в таблице ровно один раз, для каждого указан результат и запись проверки; команды и ревизия позволяют повторить проверку; журнал ссылается на существующие документы; исходные неудачи и ограничения сохранены. Если коммит/PR ещё не создан, это указано прямо: нельзя придумывать ссылки или считать базовый HEAD ревизией незакоммиченных изменений. Фиксация отчётов в git выполняется вместе с обычной фиксацией изменений этапа.

Моки подходят для ошибок и бизнес-ветвлений; реальный PostgreSQL — для RLS, транзакций, гонок, миграций и удаления; реальные устройства и провайдеры — для OAuth, ссылок, камеры и жизненного цикла приложения. Универсальный процент покрытия не является критерием готовности.

Предыдущие 8–12 недель — ориентир, не подтверждённая оценка этого расширенного объёма. После этапов 0–1 отдельно оценить монорепозиторий/API, OAuth, задачи/фото, удаление и UI; после этапа 4 уточнить по фактической скорости. Срок зависит от восстановления исходной схемы, runtime worker, проверки Apple-отзыва и политики финансовых данных. Внешние доступы, модерация и включение платежей в ориентир не входят. Не трактовать подготовку монорепозитория и фоновой инфраструктуры как бесплатное дополнение к старой оценке.

Перед соответствующими этапами потребуются доступы к тестовому Supabase, Apple Developer/App Store Connect, Google Play Console, OAuth-настройкам Google/Яндекса и домену. Секреты передаются через секрет-хранилище окружения, не через код или документацию. Отсутствие Apple-доступа не мешает работе над этапами 0–3 и кодом этапа 4, но блокирует завершение приёмки подписанной iOS-сборки на этапе 4 и реального Apple-входа на этапе 5.

| До этапа 11 | Google Play Console, регистрация/проверка владельца аккаунта, доступ к приложению; готовность пройти требуемое магазином тестирование | Доступен трек распространения и выполнены требования именно этого аккаунта. Для локальной Android-сборки Play Console не нужен |
| Этап 11 | Название/описание, право на используемый бренд, опубликованные privacy/support/deletion страницы; решение о финальной отправке в магазины | Материалы соответствуют сборке; владелец подтверждает публикацию и выполняет действия аккаунта, недоступные агенту |

Покупка подписок сервисов, регистрация владельца, юридические подтверждения и действия 2FA остаются за владельцем. Существующие оплаченные аккаунты используем повторно. Доступы запрашиваются к конкретному этапу с минимально необходимыми правами; заранее выдавать все ключи не требуется.

### Уточнение владельца: тестовый выпуск от физлица

Текущий объём — перенос существующих функций без покупок плюс уже согласованные Apple-вход и удаление аккаунта. Организацию для первого технического тестирования не создаём. Сначала development builds и TestFlight / тестовое распространение Android, затем отдельное решение о публичной подаче. Цель по географии — все доступные страны, без разработки новых языков сверх русского и английского в этом MVP.

Apple допускает Individual enrollment; в публичном App Store имя продавца будет юридическим именем владельца. Для TestFlight используем Apple Developer Program. Источник: [Apple enrollment](https://developer.apple.com/programs/enroll/).

Для новых личных Google Play-аккаунтов, созданных после 13 ноября 2023 года, перед запросом production access требуется закрытый тест с минимум 12 участниками, непрерывно подключёнными 14 дней. Это не условие начала разработки или внутреннего тестирования. Источник: [Google Play testing requirements](https://support.google.com/googleplay/android-developer/answer/14151465).

Приёмка этого решения: первый тестовый релиз устанавливается на оба телефона без публичной публикации и без покупок; Apple-вход и удаление остаются обязательными к завершению MVP. Фактические требования регистрации и доступность распространения проверяются для аккаунта владельца перед подачей.
