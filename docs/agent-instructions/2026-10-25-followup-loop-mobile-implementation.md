# Агенту реализации: Follow Up Loop — мобильное приложение

Задача: реализуй нативный интерфейс «Цикла наблюдения» в Expo-приложении `apps/mobile` по последним макетам и эргономическому ревью. Нужны рабочие компоненты React Native и интеграция с доступными данными. Веб-клиент в эту задачу не входит. Публикация сборок, OTA, деплой и merge не запрошены.

## Источники и приоритет

1. Эта инструкция и [эргономическое ревью](../design/followup-loop-mobile-v1/ergonomics-review.md) — последние решения пользователя. Они заменяют раннюю форму с постоянно открытым полем, четырьмя подсказками и кнопкой в конце прокрутки.
2. [Галерея приложения](../design/followup-loop-mobile-v1/index.html), [обзор](../design/followup-loop-mobile-v1/overview.png), [README](../design/followup-loop-mobile-v1/README.md), [карта состояний](../design/followup-loop-mobile-v1/screen-map.md).
3. [Мобильная дизайн-спецификация](../design/mobile-design-spec.md), текущие `apps/mobile/src/ui/theme.ts` и компоненты приложения.
4. [Отчёт проверки макетов](../verification/followup-loop-mobile-design-2026-10-25.md) — только визуальная галерея, не готовность нативного приложения.

Не используй файлы `followup-loop-v1/*-mobile.png` как макеты приложения: это узкая веб-версия. Нужен именно `followup-loop-mobile-v1/`.

## Сначала проверь состояние проекта

1. Прочитай корневой AGENTS.md, локальные инструкции целевого приложения и `docs/mobile-api-plan.md`. Проверь git status: рядом могут лежать незакоммиченные макеты и чужие изменения, их не удалять и не перезаписывать.
2. Найди актуальный `docs/plans/followup-loop/README.md`, если он появился. На момент подготовки этих инструкций его нет в текущем checkout и в исходной рабочей копии дизайн-брифа. Макеты не заменяют спецификацию серверной логики.
3. Проверь существующие контракты, API и реализацию случая наблюдения. Определи, что уже доступно: создание/закрытие случая, расписание, отметки, группировка истории, сохранение в медкарту, связь повторной проверки, баланс, отмена и скрытие напоминаний. Не выдумывай маршруты и поля по HTML-макету.
4. Если API есть — подключи интерфейс к нему. Если нет — сделай независимую часть интерфейса с типизированной границей данных и тестовыми сценариями вне production-пути; явно перечисли недостающие операции. Не выдавай экран с фиктивным успешным сохранением за готовую функцию. Не публикуй частично работающий сценарий. Спорные бизнес-правила согласуй до их реализации, при этом продолжай независимую UI-работу.
5. `packages/contracts` и `packages/shared` остаются переносимыми: без Next.js, DOM и серверных SDK. Не дублируй правила исходов в двух клиентах; используй утверждённый серверный результат/общую чистую функцию. Изменения контрактов согласовывай между вебом и мобильным приложением.

## Правила продукта, которые нельзя менять ради макета

| Исходная срочность | Сроки от исходной проверки | По умолчанию |
|---|---|---|
| monitor | 12 и 48 часов | включено |
| home_care | 24 и 72 часа | включено |
| urgent / emergency | на следующий день — вопрос о визите | выключено, предложить включение |
| healthy | без наблюдения | блока нет |

- Ночные отметки 21:00–09:00 переносятся на 09:00 по применимой локальной временной зоне; окончательный источник зоны и синхронизацию подтвердить по плану. Не прибавляй «ещё 48 часов» от промежуточного ответа. Показывай рассчитанную дату и время.
- У питомца один открытый случай. Включение наблюдения после новой независимой проверки закрывает предыдущий; предупреди об этом до переключения. Повторная проверка внутри случая сохраняет его связь.
- Для проверки старше 12 часов нового переключателя нет; существующий случай доступен по ссылке. В связанной повторной проверке — ссылка «Часть случая…», а не второй переключатель.
- «Лучше» закрывает случай, предлагает явно сохранить его в медкарту. Повторное сохранение не создаёт дубликаты.
- «Так же» на промежуточной отметке продолжает наблюдение; на последней направляет к врачу. «Хуже» направляет к врачу сегодня. Итог использует фиксированные правила, не вызывает модель.
- При вопросе о визите обязательны и посещение, и состояние. «Да» закрывает случай и предлагает записать визит. «Ещё нет»: urgent — врач сегодня, emergency — клиника сейчас, снова спросить завтра. Конфликтные сочетания вроде «Да» + «Хуже» сверить с утверждённым планом; не выводить приоритет из демо-кода.
- Клиника — первое действие при ухудшении. Повторная проверка с контекстом стоит 1 проверку. При нулевом балансе клиника и визит доступны, вместо повторной проверки — существующий запрос дополнительных проверок.
- «Скрыть до завтра» скрывает напоминание, не закрывает случай. «Не напоминать больше» закрывает без медицинского исхода, требует подтверждения.
- Существующие уровни срочности, медицинские ответы, дисклеймеры, юридические тексты и правила списания сохраняются. Отзыв о качестве ответа и отметка состояния — разные функции.
- FU-08 (фото в отметках и сравнение) — отдельный будущий этап. Не включай загрузку/сравнение в первую версию только потому, что есть макет.

## Граница макета и рабочего приложения

HTML/JS галереи — только визуальный и интерактивный образец, не код для переноса в production. Не копируй query-параметр демо-питомца как источник истины, setTimeout как сохранение, заглушки уведомлений, toast вместо перехода, строковые замены склонений, вымышленные даты, симптомы, возраст, баланс и ответы. Не вставляй в интерфейс пояснения «в макете…», «в продукте откроется…», «здесь сохраняются рекомендации…». Они обозначают существующее содержимое/интеграцию, которые нужно реально сохранить.

Нужны состояния: загрузка, ошибка загрузки с повтором, отправка с блокировкой повторного нажатия, ошибка с сохранённым вводом, закрытый случай, удалённый питомец/недоступный случай, нулевой баланс, отсутствие активных случаев, несколько питомцев, длинное имя и длинная история. Не раскрывай данные чужого пользователя при прямом переходе. Не считай успешное изменение локального состояния подтверждением записи на сервере.

Сроки, исходы и медицинские инструкции имеют приоритет над неоднозначными демо-датами/бейджами. Например, история случая должна показывать последнюю реальную срочность, а исход — отдельно. Демо-ссылки разных артбордов не обязаны образовывать согласованную медицинскую историю.

## Обязательная эргономика последней версии

1. **Форма.** Вверху — имя и вопрос. Контекст проверки свёрнут в строку даты/срочности; раскрытие показывает исходные симптомы. Три ответа с иллюстрациями, словами и короткими пояснениями: «Симптомы прошли или ослабли», «Без заметных изменений», «Сильнее или появились новые».
2. **Заметка.** В пустой форме только «Добавить заметку». По нажатию раскрывается поле, один плейсхолдер «Что изменилось?». Доступная подпись сообщает необязательность, даже когда визуально она не дублируется. При уже введённом тексте или ошибке поле открыто; раскрытие не теряет черновик.
3. **Лимит.** Максимум 500 символов. До 450 счётчик скрыт; начиная с 450 виден `N / 500`. Не возвращать постоянные «До 500 символов» и несколько одинаковых подсказок.
4. **Основное действие.** «Отметить» в отдельной нижней области над вкладками. На базовом размере: 20 px по бокам и снизу, 16 px сверху, кнопка минимум 52 px. Отступ от вкладок не заменяет системный safe-area. Контент формы прокручивается отдельно; в увеличенном тексте не обрезать кнопку, разрешать увеличение высоты.
5. **Клавиатура.** При открытии системной клавиатуры поле и кнопка доступны, ничего не перекрывается. Реализуй штатное keyboard avoidance, учти поведение таббара и платформенные insets; не копируй CSS fixed/100vh из галереи.
6. **Ошибка.** Сообщение об отправке находится рядом с основной кнопкой, а не вне экрана выше формы. Ввод и выбор сохраняются; после успешной отправки открывается следующий экран итога.
7. **Отступы.** Между кнопкой и следующей карточкой — 20 px, между соседними кнопками — 12 px, карточки — 20 px, вложенное действие — 18 px от содержимого. Сверять визуально, не применять слепо одинаковые margins ко всем примитивам.
8. **Длинные заголовки.** «Назад» не сжимается и имеет зону не менее 44 pt/dp; текст переносится. На Android соблюдай платформенную минимальную цель касания. Не уменьшай шрифт ради длинного имени.
9. **Доступность.** Линки/раскрытия/переключатели имеют достаточные зоны касания. У выбора есть selected-state и текст, у переключателя — роль/состояние, у ошибки — доступное объявление. Масштабирование шрифта не отключать, line-height не масштабировать дважды.

## Мобильные сценарии

- **Питомцы:** один баннер на питомца для наступившей неотвеченной отметки. Пустых баннеров нет. «Скрыть до завтра» не завершает случай. В карточке — следующий срок либо «Пора отметить».
- **Результат:** monitor/home_care включены; urgent/emergency предлагаются ниже визита и выключены. Healthy — без карточки. Системный permission prompt не вызывается автоматически на просмотре результата.
- **Разрешения:** сначала поясняющая шторка, затем ОС только по явному нажатию. Отказ/запрет ОС/ошибка сохранения не ломают in-app наблюдение. Для запрета — открытие настроек, не повторяющийся системный запрос.
- **Уведомления:** локальные, без серверного push. В тексте имя, без симптомов. Тап ведёт к нужному случаю и корректно проходит холодный старт/авторизацию/смену аккаунта. Старое уведомление закрытого случая показывает закрытое состояние; чужого/удалённого — безопасное недоступное состояние. Отмена/завершение случая убирает его pending-уведомления. Изменение с веба синхронизируется только через подтверждённую архитектуру, не обещать мгновенный фоновой эффект без неё.
- **Итог:** самостоятельный экран. «Лучше» — сохранение в медкарту по явному действию; «так же» — расписание либо клиника; «хуже» — клиника первой. Визит открывает существующую форму со связью к проверке. Цена повторной проверки видна до списания.
- **История:** одна карточка на случай; хронология с проверками, отметками, визитами, закрытием. Открытый случай имеет отметку и отключение с подтверждением. Галерея в основном показывает закрытый случай, но это не отменяет открытый.
- **Повторная проверка:** добавить плашку контекста и удаление связи в существующий шаг 1. Все прежние поля, прикрепления, черновики и шаг уточнений сохранить.
- **Медкарта:** раздел скрыт при отсутствии записей; после трёх — «Все случаи · N». В сводке врача — за последние шесть месяцев. Существующие медицинские разделы не убирать.

## Иллюстрации и визуальный стиль

[Ресурс кошки/собаки](../design/followup-loop-v1/assets/pet-moods.png) — выбранный пользователем прозрачный атлас 3 × 2. Верхний ряд кошка, нижний собака; столбцы лучше/так же/хуже. В форме размер 64 × 64, крупная иллюстрация успешного итога 130 × 130 на базовом масштабе. Не заменять стрелками, emoji или прежними контурными мордочками.

Скопируй ассеты в каталог приложения. Для React Native можно экспортировать шесть отдельных изображений по равным ячейкам атласа, сохранив прозрачность и пропорции; проверить фактические размеры и границы, не обрезать уши/усы. Не брать CSS background-position как готовую нативную реализацию. Не перекрашивать tintColor. Иллюстрации декоративные, доступные названия — текст ответов. Неизвестный вид — нейтральный текстовый fallback. Фото конкретного питомца сохраняет приоритет в профиле; иллюстрация ответа остаётся видовым символом состояния.

Используй реальные theme.ts и масштабируемые Text. Основные цвета: #FBF6EE, #FFFFFF, #F3EBDD, #E8DECB, #1F1B15, #5B5346, #767062, #0B6B5E, #DDEFEB. Не рисовать внутри приложения fake status bar, Dynamic Island, home indicator, рамку телефона и переключатель галереи.

## Порядок выполнения

Проверь контракты и навигацию → реализуй форму с раскрываемой заметкой и нижней кнопкой → исходы и связь с визитами → результат/питомцы → историю/медкарту → локальные уведомления и вход по ним. Покрой состояние кеша после мутаций, возврат и смену аккаунта. Сквозная проверка нужна на обеих платформах, а не только HTML или Expo web.

## Приёмка и отчёт

M-01. Нативные экраны сверены с PNG и последним ревью; реальные скриншоты iOS/Android приложены.
M-02. Три вкладки и существующие стеки сохранены; вход из уведомления, холодный старт, назад, авторизация и недоступные случаи работают.
M-03. Форма: обязательный выбор, обязательные ответы о визите, заметка/450/500, сохранение ввода, повторная отправка и ошибка у кнопки проверены.
M-04. Кнопка и поле доступны с клавиатурой; нет перекрытия вкладками/home indicator. Проверены 320 pt/dp, типичный 390, крупный текст 200%, длинные имена, VoiceOver/TalkBack.
M-05. Реальные сохранения, исходы, баланс, связи, история и медкарта соответствуют правилам и обновляют кеш; двойная отправка не дублирует данные/списание.
M-06. Разрешение, отказ, запрет, настройки, расписание/ночной перенос, отмена и уведомление нужного случая проверены; чужие данные не раскрываются. Указать, что реально проверено на устройстве, а что только тестом.
M-07. Кошка/собака, прозрачные ассеты, масштабирование и темы текущего приложения сохранены; заглушки галереи отсутствуют.
M-08. Пройдены актуальные typecheck и затронутые тесты; проверить package.json (`npm run typecheck --workspace @lapka/mobile`, `npm run test --workspace @lapka/mobile`). При изменении нативных зависимостей/ассетов/роутинга выполнить подходящие export/build проверки обеих платформ. Ничего не публиковать.
M-09. В `docs/verification/followup-loop-mobile-implementation.md` перечислены M-01…M-09, команды, результаты, реальные скриншоты, платформенные ограничения и недостающие API. Не считать HTML-отчёт приёмкой приложения. Если есть соответствующие этапы roadmap, проверить и их критерии.
