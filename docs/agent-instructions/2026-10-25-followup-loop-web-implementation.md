# Агенту реализации: Follow Up Loop — веб

Задача: реализуй веб-интерфейс «Цикла наблюдения» в `apps/web` по текущим макетам. Нужны настоящие компоненты, маршруты и интеграция с доступными данными, а не новая галерея. Мобильный Expo-клиент в эту задачу не входит. Деплой, публикация и merge не запрошены.

## Источники и приоритет

1. Эта инструкция фиксирует решения пользователя: отдельная страница отметки, существующий стиль кабинета, иллюстрации кошки/собаки вместо стрелок и контурных мордочек.
2. [Кликабельная галерея](../design/followup-loop-v1/index.html), [решения](../design/followup-loop-v1/README.md), [карта экранов и состояния](../design/followup-loop-v1/screen-map.md).
3. [Веб-дизайн](../design/web-design-spec.md), [октябрьские изменения](../design/web-update-2026-10-20/README.md) и фактические компоненты checkout.
4. [Проверка макетов](../verification/followup-loop-design-2026-10-25.md) подтверждает только галерею, не реализацию продукта.

Перед кодом в `apps/web` обязательно прочитай соответствующие руководства установленного Next.js в `node_modules/next/dist/docs/` от корня. Не опирайся на старые предположения о Next.js.

Эргономическое ревью мобильного приложения НЕ было автоматически применено к веб-макетам. Веб использует свою композицию: итог справа на desktop и ниже формы в узком браузере. Не копируй закреплённую мобильную панель действий и нативные вкладки в веб без отдельного решения.

## Сначала проверь состояние проекта

1. Прочитай корневой AGENTS.md, локальные инструкции целевого приложения и `docs/mobile-api-plan.md`. Проверь git status: рядом могут лежать незакоммиченные макеты и чужие изменения, их не удалять и не перезаписывать.
2. Найди актуальный `docs/plans/followup-loop/README.md`, если он появился. На момент подготовки этих инструкций его нет в текущем checkout и в исходной рабочей копии дизайн-брифа. Макеты не заменяют спецификацию серверной логики.
3. Проверь существующие контракты, API и реализацию случая наблюдения. Определи, что уже доступно: создание/закрытие случая, расписание, отметки, группировка истории, сохранение в медкарту, связь повторной проверки, баланс, отмена и скрытие напоминаний. Не выдумывай маршруты и поля по HTML-макету.
4. Если API есть — подключи интерфейс к нему. Если нет — сделай независимую часть интерфейса с типизированной границей данных и тестовыми сценариями вне production-пути; явно перечисли недостающие операции. Не выдавай экран с фиктивным успешным сохранением за готовую функцию. Не публикуй частично работающий сценарий. Спорные бизнес-правила согласуй до их реализации, при этом продолжай независимую UI-работу.
5. `packages/contracts` и `packages/shared` остаются переносимыми: без Next.js, DOM и серверных SDK. Не дублируй правила исходов в двух клиентах; используй утверждённый серверный результат/общую чистую функцию. Изменения контрактов согласовывай между вебом и мобильным приложением.

## Правила продукта, которые нельзя менять ради макета

| Исходная срочность | Сроки от исходной проверки | По умолчанию |
|---|---|---|
| monitor | 12 и 48 часов | включено |
| home_care | 24 и 72 часа | включено |
| urgent / emergency | на следующий день — вопрос о визите | выключено, предложить включение |
| healthy | без наблюдения | блока нет |

- Ночные отметки 21:00–09:00 переносятся на 09:00 по применимой локальной временной зоне; окончательный источник зоны и синхронизацию подтвердить по плану. Не прибавляй «ещё 48 часов» от промежуточного ответа. Показывай рассчитанную дату и время.
- У питомца один открытый случай. Включение наблюдения после новой независимой проверки закрывает предыдущий; предупреди об этом до переключения. Повторная проверка внутри случая сохраняет его связь.
- Для проверки старше 12 часов нового переключателя нет; существующий случай доступен по ссылке. В связанной повторной проверке — ссылка «Часть случая…», а не второй переключатель.
- «Лучше» закрывает случай, предлагает явно сохранить его в медкарту. Повторное сохранение не создаёт дубликаты.
- «Так же» на промежуточной отметке продолжает наблюдение; на последней направляет к врачу. «Хуже» направляет к врачу сегодня. Итог использует фиксированные правила, не вызывает модель.
- При вопросе о визите обязательны и посещение, и состояние. «Да» закрывает случай и предлагает записать визит. «Ещё нет»: urgent — врач сегодня, emergency — клиника сейчас, снова спросить завтра. Конфликтные сочетания вроде «Да» + «Хуже» сверить с утверждённым планом; не выводить приоритет из демо-кода.
- Клиника — первое действие при ухудшении. Повторная проверка с контекстом стоит 1 проверку. При нулевом балансе клиника и визит доступны, вместо повторной проверки — существующий запрос дополнительных проверок.
- «Скрыть до завтра» скрывает напоминание, не закрывает случай. «Не напоминать больше» закрывает без медицинского исхода, требует подтверждения.
- Существующие уровни срочности, медицинские ответы, дисклеймеры, юридические тексты и правила списания сохраняются. Отзыв о качестве ответа и отметка состояния — разные функции.
- FU-08 (фото в отметках и сравнение) — отдельный будущий этап. Не включай загрузку/сравнение в первую версию только потому, что есть макет.

## Граница макета и рабочего приложения

HTML/JS галереи — только визуальный и интерактивный образец, не код для переноса в production. Не копируй query-параметр демо-питомца как источник истины, setTimeout как сохранение, заглушки уведомлений, toast вместо перехода, строковые замены склонений, вымышленные даты, симптомы, возраст, баланс и ответы. Не вставляй в интерфейс пояснения «в макете…», «в продукте откроется…», «здесь сохраняются рекомендации…». Они обозначают существующее содержимое/интеграцию, которые нужно реально сохранить.

Нужны состояния: загрузка, ошибка загрузки с повтором, отправка с блокировкой повторного нажатия, ошибка с сохранённым вводом, закрытый случай, удалённый питомец/недоступный случай, нулевой баланс, отсутствие активных случаев, несколько питомцев, длинное имя и длинная история. Не раскрывай данные чужого пользователя при прямом переходе. Не считай успешное изменение локального состояния подтверждением записи на сервере.

Сроки, исходы и медицинские инструкции имеют приоритет над неоднозначными демо-датами/бейджами. Например, история случая должна показывать последнюю реальную срочность, а исход — отдельно. Демо-ссылки разных артбордов не обязаны образовывать согласованную медицинскую историю.

## Композиция и поведение

1. **Результат.** Для monitor/home_care карточка после срочности/клиники перед рекомендациями. Для urgent/emergency — ниже, после действия записи визита; выключена по умолчанию. Выключение/включение сохраняется, ошибка возвращает предыдущий статус и объясняет неудачу. Web-push не добавлять. Не обещать доставку локального уведомления только по факту установки приложения: проверить реальную синхронизацию.
2. **Обзор.** Перед приветственной панелью — максимум два баннера, по одному на питомца, дальше «Ещё N случаев». Три ответа ведут на страницу отметки с предвыбором, не сохраняют сразу. Эскалация меняет приоритет на клинику. Отсутствие случаев не создаёт пустую карточку.
3. **Отметка.** Самостоятельная защищённая страница с прямым URL. Слева форма, справа контекст до отправки и итог после успешной отправки. В узком браузере итог ниже формы, с переносом фокуса/объявлением. Один ответ, необязательная заметка до 500 символов. Выбор подписан и виден независимо от цвета. Не переделывать в чат.
4. **История/лента.** Одна строка на случай; самостоятельные проверки сохраняют прежний вид. Лента слева, питомец/действия справа. Открытый случай разрешает отметку и отключение с подтверждением; закрытый — только подходящие действия. Визиты и проверки ведут на реальные записи.
5. **Медкарта.** «Перенесённые случаи» рядом с визитами; до трёх строк и переход ко всем. Пустой раздел скрыт. Сводка врача — случаи за шесть месяцев.
6. **Повторная проверка.** Плашка «Учтём проверку… и N отметок» с явным удалением связи. Полный существующий состав формы остаётся. Цена видна до отправки. Данные прошлого случая не выдаются за новый пользовательский ввод.

## Порядок выполнения

Сначала составь краткую карту существующих данных/контрактов и недостающих интеграций. Затем реализуй общие компоненты, страницы отметки/итога, карточку результата и баннеры, историю/ленту, медкарту и повторную проверку. Подключи реальные операции и обработку ошибок. После каждого связного блока проверяй затронутый сценарий. Не заменяй весь кабинет ради новой функции.

## Приёмка и отчёт

W-01. Стиль и композиция сверены со всеми применимыми PNG на 1440/390/320 px; приложены фактические скриншоты реализации.
W-02. Прямой URL, обновление страницы, переходы назад и авторизация работают; чужой случай не раскрывается.
W-03. Переключатель, баннеры, предвыбор, сохранение отметки и ошибки связаны с реальными данными; двойной клик не создаёт дубли.
W-04. Все ветки исходов, визит и нулевой баланс соответствуют утверждённым правилам; повторная проверка списывает ровно одну проверку через существующий механизм.
W-05. История не дублирует связанные проверки; медкарта/сводка и ссылки на визиты согласованы.
W-06. Работают кошка/собака, длинные имена, пустые данные, длинная лента и 200% текста. Keyboard/focus, доступные подписи и нижняя навигация не мешают действиям.
W-07. Пройдены актуальные lint/typecheck/затронутые тесты; сборка если изменены роуты/серверные границы. Команды проверить в package.json (`npm run lint`, `npm run typecheck`, `npm run test --workspace @lapka/web`, `npm run build --workspace @lapka/web`). Тестировать правила и поведение, не копии HTML.
W-08. В `docs/verification/followup-loop-web-implementation.md` записаны W-01…W-08, команды, результаты, реальные скриншоты, недостающие API и ограничения. Не помечать заблокированный сценарий выполненным. Если работа относится к этапам roadmap, сопоставить также их критерии; этот список их не отменяет.

В финале перечисли изменения, проверки, ссылки на отчёт/скриншоты и оставшиеся зависимости. Не деплой и не merge без отдельной инструкции.
