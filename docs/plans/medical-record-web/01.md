## Сделать

Изучить текущие contracts, API, мобильную реализацию и отчёты MR-01…11. До изменения Next.js прочитать соответствующие руководства в node_modules/next/dist/docs/. Уточнить текущий способ авторизации веб-клиента и подключить существующий API-клиент; не копировать native-хранилище токенов.

Создать страницу /pets/[id] и переход к ней из списка; сохранить редактирование /pets/[id]/edit. Подключить getHealthOverview и getPet. Собрать адаптивный каркас: шапка питомца, сроки, важное, пять медицинских разделов, история проверок, действия. На первом этапе карточки показывают реальные доступные данные; неготовые действия скрыть под флагом этапа.

Поддержать загрузку, пустой профиль, отказ доступа, ошибку с повтором и сохранёнными данными. Ссылка на анкету не заменяет медкарту. Неизвестную дату веса/прививки не выдумывать.

## Приёмка

1. Владелец открывает свою медкарту по прямой ссылке и после перезагрузки.
2. Чужой petId и выход из аккаунта не раскрывают данные; проверить UI и запрос API.
3. Для Мурки видны данные сервера, для Бобика — «из анкеты», без фиктивных дат.
4. На 390 и 1440 px нет горизонтального скролла; навигация и действия доступны с клавиатуры.
5. Ошибка запроса даёт повтор, а не пустую «здоровую» медкарту.

## Как закрыть этап

Продемонстрировать сценарии приёмки на реальном API с тестовым владельцем и отдельным чужим владельцем для проверки доступа. Для изменённой логики добавить полезные интеграционные/компонентные проверки; не тестировать совпадение CSS с самим собой. Выполнить доступные typecheck/lint и релевантные тесты текущего workspace, указав точные команды и результат.

Создать `docs/verification/medical-record-web-01.md`: commit/окружение, критерий → доказательство, скриншоты 390 и 1440, выполненные тесты, дефекты/непроверенные пункты. Не закрывать критерий без проверки. Не переключаться к следующему этапу при незакрытом обязательном критерии; описать блокер и его минимальное исправление. Не менять опубликованные данные и не деплоить без отдельного запроса.
