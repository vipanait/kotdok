# SEO-страницы по симптомам: итерационный план

> Для исполняющего агента: использовать `superpowers:executing-plans` и выполнять один выбранный этап за раз. Этот документ — план, а не разрешение реализовать сразу все этапы.

Дата плана: 25 октября 2026. Статус: план, ни один этап не реализован.

**Цель:** привлекать владельцев кошек и собак из поиска (Яндекс, Google) на статические страницы по симптомам и отравлениям. На странице есть бесплатный блок «Это срочно?», который считается по правилам в браузере. Призыв к действию ведёт на регистрацию, где даются 2 бесплатные проверки.

**Ограничение по бюджету:** анонимные проверки через модель запрещены. Страницы и блок «Это срочно?» не вызывают модель и не делают запросов к API. Модель участвует только в подготовке черновиков текста, до вычитки ветеринаром.

**Архитектура:** отдельная группа маршрутов `app/(content)` со своим статическим корневым layout (только `ru`), контент в JSON-файлах репозитория с проверкой схемой Zod, `generateStaticParams` + `dynamicParams = false`, отдельная статическая CSP для этих путей, прокси Next (`src/proxy.ts`) на них не запускается. Главная и приложение остаются как есть.

**Стек:** текущий `apps/web` (Next.js 16.3.8, React 19, Zod, Vitest). Новых зависимостей план не требует, кроме `@vercel/analytics` на этапе SEO-05. Перед кодом исполнитель читает гайды из `node_modules/next/dist/docs/` (список ниже) и `AGENTS.md`.

## Проверка индексации

Проверено 25 октября 2026 года. Вывод: **индексация не заблокирована**. Ни Vercel, ни ru-proxy не отдают поисковым роботам challenge или 403.

### Настройки Vercel (только чтение)

Vercel MCP не имеет доступа к команде `panaitvi-4639s-projects` (ответ 403), поэтому настройки прочитаны через `vercel api` и `vercel firewall`:

- Firewall: «Not configured». Активного конфига нет (`/v1/security/firewall/config/active` отвечает 404), то есть нет ни пользовательских правил, ни managed rulesets (Bot Protection, AI Bots).
- Attack Challenge Mode выключен. `attack-status` за последние сутки: `anomalies: []`.
- System Bypass: два правила уровня проекта на все домены — для `51.250.0.247` (старый прокси в Yandex Cloud) и `90.156.157.146` (Selectel).
- Неопубликованный черновик: одно правило для `51.250.0.247` с действием `log`. Оно не опубликовано и ничего не блокирует.
- System Mitigations (DDoS-защита платформы) активны, но IP прокси от них освобождён.
- В runtime-логах production за 72 часа нет ни одного ответа 403.
- Защита деплоев: `ssoProtection: all_except_custom_domains`, на `lapka.my` она не действует. Парольной защиты нет.

YandexBot есть в справочнике verified bots Vercel ([Bot Management](https://vercel.com/docs/bot-management#verified-bots), раздел Verified bots directory). Но Vercel видит у всех запросов IP прокси, а не IP Яндекса, поэтому проверить бота по IP или обратному DNS он не может. Из этого два следствия:

1. Для Vercel запрос curl с поддельным UA через прокси неотличим от настоящего робота. Поэтому замер выше показателен и для настоящих роботов, кроме проверок, которые делает сам прокси.
2. Bot Protection и Attack Mode при работающем прокси включать нельзя без отдельной проверки. Документация Vercel прямо пишет, что Bot Protection за reverse proxy не работает корректно, а verified bots за прокси не распознаются.

### ru-proxy

В `infra/ru-proxy/lapka.conf` нет `limit_req`, `limit_conn`, фильтров по User-Agent и `deny`. Запросы для `lapka.my` и `www.lapka.my` проксируются целиком. Логи доступа на самом сервере не читались: SSH на боевой сервер в этой сессии не разрешён. Это проверяет владелец, команда ниже.

### Что не блокирует индексацию, но важно

1. **`www.lapka.my` отвечает 200, а не редиректом.** Получается дубль сайта. Canonical указывает на `https://lapka.my`, так что вред ограничен, но поисковикам лучше видеть 301/308. Исправление (решение владельца): Vercel → проект kotdok → Settings → Domains → `www.lapka.my` → Redirect to `lapka.my` (308). Через прокси это тоже работает, потому что он передаёт `Host`.
2. **Весь сайт рендерится динамически.** Корневой layout читает cookie `NEXT_LOCALE`, а `src/proxy.ts` ставит CSP с nonce. По документации Next nonce требует динамического рендеринга всех страниц. Функции выполняются в `hnd1` (Токио, `vercel.json`), поэтому TTFB главной через прокси 1,3–2,2 с. Для новых страниц это решает этап SEO-01: они отдаются из CDN.
3. **Единственная точка отказа.** Весь поисковый трафик идёт через одну ВМ в Selectel (1 vCPU 20 %). Если ВМ упадёт, роботы получат ошибку соединения. Короткие сбои поисковики переносят, длинные — нет. Нужен внешний мониторинг доступности `https://lapka.my/robots.txt`.
4. **Пути `/cats` и `/check` закрыты в robots.txt по префиксу.** Новые адреса не должны начинаться с них: например, `/cats-…` или `/checklist` тоже окажутся закрыты.

### Что подтверждает только владелец

Подтвердить, что настоящий робот из сетей поисковика получает 200, могут только сами поисковики:

1. **Яндекс.Вебмастер** (webmaster.yandex.ru):
   1. Добавить сайт `https://lapka.my` и подтвердить права DNS-записью TXT в Cloudflare (или мета-тегом, но для него нужен деплой).
   2. Инструменты → «Проверка ответа сервера»: URL `https://lapka.my/`, робот «YandexBot». Ожидается код 200 и HTML страницы. То же для `https://lapka.my/robots.txt` и `https://lapka.my/sitemap.xml`.
   3. Индексирование → «Файлы Sitemap»: добавить `https://lapka.my/sitemap.xml`.
   4. Индексирование → «Зеркала сайта»: главное зеркало — `lapka.my` без www.
   5. Через несколько дней: «Статистика обхода» без ошибок 4xx/5xx на публичных страницах.
2. **Google Search Console** (search.google.com/search-console):
   1. Добавить ресурс «Домен» `lapka.my` и подтвердить его TXT-записью в Cloudflare.
   2. «Проверка URL» → `https://lapka.my/` → «Проверить страницу на сайте». Ожидается «URL доступен для Google», а на снимке «Просмотреть проверенную страницу» — настоящая главная, не Security Checkpoint.
   3. «Файлы Sitemap» → добавить `sitemap.xml`.
3. **Логи прокси.** Зайти на ВМ (`ssh root@90.156.157.146`) и проверить, что запросы роботов получают 200. Команда печатает IP и код ответа, формат лога — `log_format lapka` в `infra/ru-proxy/lapka.conf`:

   ```sh
   grep -iE 'YandexBot|Googlebot' /var/log/nginx/lapka.access.log | awk '{split($0,a,"\""); split(a[5],b," "); print $1, b[1]}' | sort | uniq -c | sort -rn | head -20
   ```

   Подлинность адреса проверяется обратным DNS: `host <ip>` должен вернуть `*.yandex.ru`, `*.yandex.net`, `*.yandex.com`, `*.googlebot.com` или `*.google.com`.

Эти шаги входят в этап SEO-00. Повторять их нужно после каждой смены IP прокси или DNS.

## Решения

### Маршруты

| Путь | Что | Количество |
|---|---|---|
| `/simptomy` | Общий хаб: «когда сразу в клинику», ссылки на кошек и собак | 1 |
| `/simptomy/koshki`, `/simptomy/sobaki` | Хабы по виду, симптомы сгруппированы по системам организма | 2 |
| `/simptomy/[slug]` | Страница симптома для одного вида, например `rvota-u-koshki` | ~47 |
| `/otravlenie` | Хаб токсичных веществ | 1 |
| `/otravlenie/[slug]` | Вещество с разделами для кошек и собак, например `liliya` | 6 |
| `/veterinarnaya-proverka` | Кто и как проверяет материалы, данные ветеринаров | 1 |

Почему так:

- В slug стоит вид (`-u-koshki`, `koshka-…`). Ключевые слова попадают в URL, а у страниц для кошек и собак разные адреса и разный текст: это не дубли.
- Статические сегменты `koshki` и `sobaki` в Next имеют приоритет над `[slug]`. Тест запрещает slug, совпадающие с ними.
- Страницы отравлений — по веществу, а не по виду: человек ищет «собака съела шоколад», а различия между видами помещаются в разделы одной страницы. У лилии есть только раздел для кошек.
- Ни один путь не начинается с `/cats` или `/check` (см. robots.txt).

### Статическая генерация (Next.js 16)

Прочитанные гайды: `01-app/02-guides/public-static-pages.md`, `content-security-policy.md`, `json-ld.md`, `mdx.md`, `analytics.md`; `03-api-reference/04-functions/generate-static-params.md`, `generate-metadata.md`; `03-file-conventions/layout.md`, `not-found.md`, `01-metadata/sitemap.md`, `robots.md`, `opengraph-image.md`.

Сейчас статическая страница невозможна по двум причинам:

1. `app/layout.tsx` вызывает `getLocale()` → `cookies()`, и всё дерево становится динамическим.
2. `src/proxy.ts` ставит CSP с nonce. Гайд по CSP: «When you use nonces in your CSP, all pages must be dynamically rendered».

Решение:

- **Несколько корневых layout** (`layout.md`, «multiple root layouts»): текущий `app/layout.tsx` переезжает в `app/(frontend)/layout.tsx` без изменений, новый `app/(content)/layout.tsx` статический — `<html lang="ru">`, те же шрифты и `globals.css`, без `LocaleProvider` с cookie. Переход между группами — полная загрузка страницы. Это допустимо: со страниц контента уходят только на регистрацию.
- **404 без общего корня:** `app/global-not-found.tsx` с `experimental.globalNotFound` (`not-found.md`) либо отдельные `not-found.tsx` в группах. Выбор фиксируется в отчёте SEO-01. Сейчас 404 отдаёт `noindex`, так и должно остаться.
- **`generateStaticParams` возвращает только опубликованные slug, `dynamicParams = false`.** Неизвестный или неопубликованный адрес даёт 404, а не рендер по запросу.
- **Прокси не запускается на путях контента.** В `config.matcher` из `src/proxy.ts` исключаются `simptomy`, `otravlenie`, `veterinarnaya-proverka`. Заодно на этих страницах не идёт запрос `supabase.auth.getUser()` и не ставятся cookie.
- **CSP для путей контента** задаётся в `next.config.ts` `headers()` без nonce. Next в App Router всегда вставляет inline-скрипты с данными RSC, поэтому нужен либо `'unsafe-inline'` для `script-src` только на этих путях, либо хеши. На этапе SEO-01 сначала проверяется `experimental.sri` (гайд CSP, раздел Subresource Integrity), и если он не закрывает inline-скрипты, применяется вариант с `'unsafe-inline'`. Почему это приемлемо: страницы не выводят пользовательский ввод и параметры запроса, контент берётся только из репозитория, JSON-LD экранируется (`<` → `<`, гайд JSON-LD), сторонних скриптов нет. Изменение CSP касается безопасности, поэтому решение подтверждает владелец в отчёте SEO-01. Для остальных страниц nonce-CSP не меняется.
- **Metadata:** `generateMetadata` даёт title, description, `alternates.canonical`, `openGraph`. Существующие `app/opengraph-image.tsx` и `twitter-image.tsx` остаются для всего сайта. Их разметка выносится в общую функцию (например, `src/shared/og-card.tsx`), а `simptomy/[slug]/opengraph-image.tsx` и `otravlenie/[slug]/opengraph-image.tsx` вызывают её с заголовком страницы. Шаблон тот же, новой картинки нет.
- **`sitemap.ts`** добавляет хабы и опубликованные страницы с `lastModified = reviewedAt`. **`robots.ts`** не меняется по смыслу: новые пути открыты. Тест проверяет, что ни один опубликованный путь не попадает под `disallow`.

### Формат контента: JSON, не MDX

Файлы `apps/web/content/symptoms/<slug>.json`, `apps/web/content/toxins/<slug>.json`, `apps/web/content/reviewers/<id>.json`. Схема Zod — в `apps/web/src/features/seo-content/schema.ts`.

Почему JSON:

- Страница — это в основном структура, а не свободный текст: признаки по 5 уровням, вопросы «да/нет» с уровнем, причины по возрасту, вопросы FAQ, статус вычитки. Из этих же полей собираются JSON-LD (FAQPage, `reviewedBy`, `lastReviewed`) и правила блока «Это срочно?». В MDX их пришлось бы дублировать во frontmatter или разбирать из разметки.
- Схема проверяется тестом и при сборке. Пропущенный уровень, вопрос без уровня или страница без ветеринара не проходят CI.
- Не нужны `@next/mdx`, MDX-компоненты и настройка компилятора (гайд `mdx.md`). Меньше поверхности для ошибок и для `'unsafe-inline'`.
- Ветеринар правит текст не в файле, а на предпросмотре (см. «Процесс контента»), поэтому удобство Markdown для автора не решает.

Текстовые поля — простые строки и массивы абзацев без HTML. Ссылки на другие страницы задаются полем `related: [slug]`, а не в тексте.

### Только ru

- Цель — поиск Яндекса и русскоязычный Google. Английская версия требует второй вычитки ветеринаром (в два раза дороже) и конкурирует с PetMD, VCA и другими крупными ресурсами.
- Локаль сайта сейчас хранится в cookie, без префиксов в URL. Английские страницы потребовали бы `/en/…`, `hreflang` и второй набор slug.
- В схеме есть поле `locale: 'ru'`, так что английскую версию можно добавить позже, не меняя модель.

### Устройство страницы симптома

1. **H1 и подпись.** «Рвота у кошки: когда срочно к врачу». Под заголовком: «Проверено: <ветеринарный врач Ф. И. О.>, <дата проверки>», ссылка на `/veterinarnaya-proverka`, дата обновления.
2. **Короткий ответ**, 40–60 слов: когда сразу в клинику, когда можно наблюдать. Это текст, который должен попасть в сниппет.
3. **Признаки по уровням срочности.** Пять блоков в порядке `URGENCY_KEYS` (`apps/web/src/shared/utils/urgency.ts`). Название и инструкция уровня берутся из словаря `urgency` в `apps/web/src/shared/i18n/dictionaries/ru.ts` — «ЭКСТРЕННО — Немедленно в ветеринарную клинику», «СРОЧНО — К ветеринару в течение 24 часов» и так далее, — а не пишутся заново. Признаки в блоках согласуются с правилами в `apps/web/src/server/symptom-check/analyze-symptom-check.ts`. Цвет уровня — из тех же CSS-классов, и уровень никогда не показывается только цветом.
4. **«Это срочно?»** — 5–7 вопросов «да/нет» (подробнее ниже).
5. **Частые причины по возрасту**: котёнок/щенок, взрослый, пожилой. Пишется «может быть связано с», «частые причины», а не «у вашей кошки».
6. **Что сделать дома до визита**: безопасные шаги и отдельный список «чего не делать». Без лекарств из домашней аптечки и без доз.
7. **Что сказать врачу**: чек-лист — когда началось, как часто, что ел, фото или видео, прививки, вес. Его можно скопировать.
8. **Призыв к действию.** Текст вроде «Опишите, что происходит, — Лапка учтёт возраст, породу и историю питомца. После регистрации 2 проверки бесплатно» ведёт на `/register?next=/pets/new` (`next` уже поддерживает `features/auth/AuthRoute.tsx`). Рядом ссылки на приложение из `apps/web/src/shared/app-store-links.ts`.
9. **FAQ** из 3–5 вопросов, видимых на странице.
10. **Связанные симптомы, источники, `DISCLAIMER`** из `analysis-language.ts` дословно, в конце страницы и под результатом блока «Это срочно?».

Страница отравления устроена так же, но вместо причин по возрасту — «сколько опасно» (без расчёта доз, только «любое количество — повод позвонить в клинику», если так считает ветеринар), «первые часы» и «чего не делать» (например, не вызывать рвоту без указания врача).

**JSON-LD** (каждый блок экранируется):

- `MedicalWebPage`: `name`, `description`, `url`, `inLanguage: ru`, `lastReviewed`, `reviewedBy` (`Person`, `jobTitle` «Ветеринарный врач», `url` на страницу проверки), `about`, `publisher` → `@id` организации, которая уже описана в корневом layout.
- `BreadcrumbList`.
- `FAQPage` только с вопросами, видимыми на странице.

Google с 2023 года показывает расширенные сниппеты FAQ только авторитетным государственным и медицинским сайтам, так что на них рассчитывать не стоит. Разметка всё равно проверяется валидатором Schema.org и инструментом проверки микроразметки в Яндекс.Вебмастере.

### Блок «Это срочно?»

- Вопросы и их уровни лежат в JSON страницы: `{ text, level: 'emergency' | 'urgent' }`. Ответ «да» на вопрос уровня `emergency` сразу показывает ЭКСТРЕННО, не дожидаясь остальных ответов. Иначе после всех ответов результат — самый срочный уровень среди ответов «да». Если «да» нет ни одного, результат — НАБЛЮДАЕМ с текстом «по этим вопросам срочных признаков нет; наблюдайте 48 часов, при ухудшении — к врачу».
- Блок никогда не выдаёт ДОМАШНИЙ УХОД и ВСЁ В ПОРЯДКЕ. Он не видит питомца, а ложное успокоение — самая опасная ошибка. Эти уровни описаны только в тексте страницы.
- Функция расчёта — чистая, в `apps/web/src/features/seo-content/quiz.ts`, с юнит-тестами. Компонент — клиентский остров на статической странице. Ответы не отправляются никуда, кроме необязательного события аналитики с уровнем результата (SEO-05), без текста ответов.
- Под результатом: инструкция уровня из словаря, `DISCLAIMER` и призыв к действию. При ЭКСТРЕННО призыв к регистрации не главный: первым идёт «Езжайте в клинику сейчас».

## Процесс контента

| Шаг | Кто | Статус в JSON |
|---|---|---|
| 1. Бриф: тема, вид, запросы из таблицы, связанные страницы | редактор (владелец или агент) | `brief` |
| 2. Черновик по схеме. Модели передаются определения уровней из `analyze-symptom-check.ts` и правила формулировок ниже | модель | `draft`, `draftedBy: model` |
| 3. Самопроверка: схема, длина, запрещённые слова, совпадение уровней со словарём (автоматический тест) | агент | `draft` |
| 4. Вычитка на предпросмотре Vercel (`noindex`), правки текстом или комментариями | ветеринар | `vet_review` |
| 5. Правки внесены, ветеринар письменно подтверждает итоговый текст | ветеринар | `vet_approved`, `reviewer`, `reviewedAt` |
| 6. Публикация: проверка продукта, призыва к действию и юридических формулировок | владелец | `published`, `publishedAt` |

- Статус хранится в блоке `review` файла страницы: `status`, `reviewer` (id из `content/reviewers`), `reviewedAt`, `nextReviewAt` (по умолчанию +12 месяцев), `approvedBy` (владелец), `publishedAt`. Историю правок даёт git: каждый переход статуса — отдельный коммит в PR. Подтверждение ветеринара — цитата или ссылка в описании PR.
- Утверждают двое: ветеринар отвечает за медицинскую точность, владелец решает о публикации. Модель и агент не ставят `vet_approved` и `published`.
- В production попадают только страницы со статусом `published`. Тест CI падает, если у опубликованной страницы нет `reviewer`, `reviewedAt` или ветеринара из справочника. Отдельный скрипт (`npm run content:review-due`) раз в месяц выводит страницы, у которых `nextReviewAt` прошёл. Сборку он не валит, чтобы просроченная дата не ломала посторонние PR.
- Повторная вычитка нужна также, когда меняются уровни или правила в `analyze-symptom-check.ts` или словарь `urgency`.

### Требования к медицинскому контенту (YMYL)

- Каждая страница: ФИО и квалификация проверившего ветеринара (диплом, клиника, стаж — на `/veterinarnaya-proverka`), дата проверки, дата обновления, список источников (Merck Veterinary Manual, руководства WSAVA и ISFM, для ядов — ASPCA Animal Poison Control и подобные).
- Формулировки — по `DISCLAIMER`: «Лапка — информационный инструмент. Не является ветеринарным диагнозом и не заменяет осмотр специалиста.» На странице нет слов «диагноз», «диагностика», «вылечит», «лечение» в значении назначения, нет «у вашего питомца X». Пишется «возможные причины», «может быть связано с», «врач может проверить». Тест ищет запрещённые слова в текстовых полях.
- Никаких доз, препаратов для самостоятельного приёма, человеческих лекарств, «народных средств» и советов вызвать рвоту без врача.
- Сомнение решается в пользу более срочного уровня. Это то же правило, что в промпте анализа («If there is any doubt, prefer MONITOR or HOME CARE»), но для блока «Это срочно?» нижняя граница — НАБЛЮДАЕМ.
- Страницы для кошек и собак различаются по существу: свои причины, признаки и пороги. Совпадение текстов больше половины считается дублем и не публикуется (проверка в тесте на пересечение абзацев).
- Без рекламы клиник и товаров. Призыв к действию — только регистрация в Лапке и ссылки на приложение.

## Аналитика воронки

Что есть сейчас: ни Vercel Analytics, ни Яндекс.Метрики в коде нет (нет `@vercel/analytics` в `apps/web/package.json`, в CSP `connect-src` только `'self'` и Supabase). Есть служебная `/admin/statistics` (`apps/web/src/server/admin/statistics.ts`): регистрации и проверки по дням из `profiles` и `symptom_checks`.

Минимальный вариант:

1. **Поиск → страница:** Яндекс.Вебмастер и Search Console (запросы, показы, клики). Ничего ставить не нужно.
2. **Просмотры страниц:** Vercel Web Analytics (`@vercel/analytics`, компонент `<Analytics />` только в `app/(content)/layout.tsx`). Скрипт и отправка идут на свой домен (`/_vercel/insights/*`), cookie не ставятся, CSP `connect-src 'self'` достаточно. Включает владелец в Vercel → Analytics. Необязательное событие `quiz_result` с уровнем — пользовательские события доступны на Pro, команда на Pro.
3. **Страница → регистрация → первая проверка:** при клике на призыв к действию клиент ставит функциональную cookie `lapka_landing` (slug страницы, 30 дней, `SameSite=Lax`). При создании профиля сервер читает её, сверяет slug с белым списком опубликованных и пишет в новую колонку `profiles.signup_landing` (миграция). Cookie переживает вход через Google, Yandex и Apple, где параметры URL теряются, — так же уже работает `lapka_pd_consent`. В `/admin/statistics` появляется блок: регистрации с SEO-страниц по slug и доля сделавших первую проверку (`symptom_checks`) за 7 дней.

Яндекс.Метрика в минимальный вариант не входит: её cookie и Вебвизор требуют баннера согласия, обновления политики обработки ПДн и расширения CSP на `mc.yandex.ru`. К ней стоит вернуться, если трёх источников выше не хватит. Упоминание `lapka_landing` в политике конфиденциальности согласует владелец.

## Риски

1. **Нет ветеринара-рецензента.** Без него публиковать нельзя. Это решение, а не ограничение кода: загрузчик не пропустит страницы без `reviewer`. Владельцу нужно найти ветеринара (или двух — для кошек и собак) с готовностью указать ФИО и квалификацию публично.
2. **Ошибка в медицинском тексте или ложное успокоение.** Снижается вычиткой, правилом «сомнение — в сторону срочности», нижней границей НАБЛЮДАЕМ у блока «Это срочно?», отсутствием доз и повторной вычиткой раз в 12 месяцев.
3. **YMYL и новый домен.** Медицинские темы ранжируются медленно, а у домена нет истории. Первые результаты — через месяцы, а не недели. Помогают подписи ветеринара, источники и отсутствие тонких страниц.
4. **Ослабление CSP на путях контента.** Возможно `'unsafe-inline'`. Ограничено путями без пользовательских данных, решение фиксируется в SEO-01. Supabase-сессия хранится в cookie, доступных JS, поэтому любое будущее изменение, которое выводит ввод пользователя на этих страницах, требует пересмотра CSP.
5. **Единственный прокси.** Если ВМ в Selectel упадёт, сайт недоступен и для роботов. Нужен мониторинг (SEO-00.5). Если прокси сменит IP, в Vercel нужен новый System Bypass, иначе вернётся Security Checkpoint (так было 8 октября 2026).
6. **Включение Bot Protection или Attack Mode** за прокси может закрыть сайт для роботов, потому что Vercel не видит их настоящих IP. Перед включением — отдельная проверка этим же чек-листом.
7. **Дубли и каннибализация** между страницами кошек и собак и с главной. Снижаются тестом на пересечение текста и правилом «один запрос — одна страница».
8. **Перенос корневого layout** задевает весь сайт. Снижается тем, что SEO-01 — отдельный PR с полной регрессией входа, регистрации и проверок до слияния, потому что слияние в `main` деплоит production.
9. **Экспериментальные флаги Next** (`globalNotFound`, `sri`) могут измениться при обновлении. Решение и запасной вариант (`not-found.tsx` в группах, `'unsafe-inline'`) записываются в отчёте SEO-01.

```sh
npm run typecheck --workspace=@lapka/web
```

```sh
curl -s -o /dev/null -w '%{http_code} %{time_starttransfer}\n' -A 'Mozilla/5.0 (compatible; YandexBot/3.0; +http://yandex.com/bots)' https://lapka.my/simptomy/rvota-u-koshki
curl -sI https://lapka.my/simptomy/rvota-u-koshki | grep -iE 'x-vercel-(cache|mitigated)|content-security-policy|set-cookie'
```

Пути тестов создаются на своём этапе. Отсутствие тестов не считается успехом. Интеграционные тесты (SEO-05) — только на изолированной тестовой БД, по `apps/web/tests/support/db-guard.ts`.
