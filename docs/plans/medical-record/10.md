# MR-10. Учёт медкарты при проверке симптомов

> Для исполняющего агента: прочитать [общий план](README.md), исходную спецификацию и выполнить только этот этап через `superpowers:executing-plans`. Следующий этап не начинается автоматически.

**Цель:** Анализ получает ограниченную по размеру сводку актуальных медданных выбранного питомца.

**Зависит от:** 02–07; после 09 по выбранному порядку.

**Макеты:** X-check; исходная спецификация §14.

**Архитектура:** вертикальный этап: контракт → сервер/хранение → мобильный UI → проверки. Новые серверные маршруты входят в `/api/v1`; UI использует общий API-клиент.

**Стек:** текущие Expo/React Native, Next.js API, PostgreSQL, Zod, Vitest. Версии и инструкции проверяются в репозитории перед кодом.

## Файлы и границы

- `apps/web/src/server/medical-record/analysis-context.ts (новый)`
- `apps/web/src/server/symptom-check/analyze-symptom-check.ts`
- `apps/mobile/app/(tabs)/check/index.tsx`

Новые пути — предлагаемая структура. Если эквивалент уже появился, расширить его и зафиксировать фактический путь, не создавать дубль. Для миграции `<новая_метка>` заменить на следующую свободную метку времени репозитория.

## Шаги

- [ ] Зафиксировать базовые проверки и убедиться, что зависимости этапа приняты, а не просто начаты.
- [ ] Создать тестовые сценарии по MR-10.1…4 ниже; для логики данных сначала воспроизвести отсутствие/ошибку поведения на минимальном тесте.
- [ ] Выделить серверный построитель контекста: текущие курсы, последние прививки по болезням, обработки, диагнозы за год и тренд веса. Включать только необходимые поля.
- [ ] Ограничить общий объём контекста и число записей с детерминированным порядком, сохранять источники/даты. Старые диагнозы не выдавать за текущее состояние.
- [ ] Подключить контекст к существующему анализу без изменения счётчика проверок, машины задач и retry. Пользовательские заметки передавать как данные, не как инструкции модели.
- [ ] Показывать подпись «Учтём медкарту…» только когда контекст действительно включён и есть записи. При ошибке загрузки не утверждать обратное; согласованно использовать исходный профиль и фиксировать fallback.
- [ ] Зафиксировать сценарии оценки: пустая карта, давние записи, текущий курс, противоречивые/неполные данные, слишком длинные заметки.
- [ ] Запустить адресные тесты, проверки типов и регрессию затронутых старых сценариев. Проверки SQL-транзакций/RLS выполнить на изолированной тестовой базе, не ограничиваться моками.
- [ ] Сверить UI с указанными артбордами; записать доказательства для каждого критерия в `docs/verification/medical-record-10.md`. Отдельно записать то, что проверить не удалось.
- [ ] Представить рабочий результат этапа на приёмку. Незакрытые критерии означают, что этап не завершён.

## Нумерованные критерии приёмки

- [ ] **MR-10.1** Контекст содержит только выбранного pet_id, другого пользователя/питомца нет.
- [ ] **MR-10.2** Одинаковые данные дают одинаковое усечение и порядок; лимит никогда не превышается.
- [ ] **MR-10.3** Старый диагноз снабжён датой, отсутствующие данные не становятся отрицанием болезни.
- [ ] **MR-10.4** Промпт-инъекция в заметке не становится системной инструкцией; кредиты и повтор задач не регрессировали.

Предлагаемые новые файлы: `apps/web/tests/server/medical-record/stage-10.test.ts`, `apps/web/tests/integration/medical-record-10.test.ts`, `apps/mobile/src/features/medical-record/stage-10.test.ts`. Команды запуска и шаблон отчёта — в общем плане. Для MR-10 ожидается успешное выполнение каждого критерия выше, а не только зелёный общий набор тестов.
