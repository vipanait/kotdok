# Медкарта: итерационный план реализации

> Для исполняющего агента: использовать `superpowers:executing-plans` и выполнять один выбранный этап за раз. Этот документ — план, а не разрешение реализовать сразу все этапы.

**Цель:** выпускать небольшие законченные функции медкарты, каждую отдельно тестировать и принимать.

**Архитектура:** мобильный клиент Expo использует общий контракт/API-клиент, авторизованные `/api/v1` маршруты Next.js и серверные транзакции PostgreSQL. Даты, запись событий и синхронизация анкеты имеют единые источники истины. Уведомления только локальные, сводка PDF формируется на устройстве.

**Стек:** существующие npm workspaces `apps/mobile`, `apps/web`, `packages/contracts`, `packages/shared`. Этот план не устанавливает зависимости и не изменяет продуктовый код.

**Спецификация:** [medical-record-spec.md](../../design/medical-record-spec.md). **Дизайн:** [решения и расхождения](../../design/medical-record-concept-v1/README.md), [чек-лист интерфейса](../../design/medical-record-concept-v1/implementation-handoff.md), [карта всех экранов](../../design/medical-record-concept-v1/screen-map.md).

## Порядок

Справочник вынесен из прививок специально: ручной ввод проверяет модель записей и планов независимо от наполнения каталога.

## Правило одной итерации

1. Передать агенту этот документ и ровно один файл этапа.
2. Агент изучает актуальные исходники, реализует этот этап вместе с нужным сервером/контрактами и выполняет его тесты.
3. Показывает работающий сценарий, изменения, ограничения и отчёт с нумерованными критериями.
4. Владелец принимает этап или возвращает конкретные замечания. Затем отдельно передаётся следующий файл.

Каждый этап — отдельный набор изменений/PR. Не выделять сначала месяц «всей базы», затем «всего UI»: этап должен давать проверяемый пользовательский результат. Возможности ещё не реализованных этапов скрыты, не имитируют успешную запись и не обещают уведомления, которых пока нет.

## Общие ограничения

- Анкета сохраняет поля и порядок. Расширения не могут ломать текущие создание/редактирование/проверки.
- Все медицинские записи принадлежат владельцу и питомцу; удалённые сущности не возвращаются. RLS проверяется реальными тестами с двумя пользователями, не только моками.
- `packages/*` остаются переносимыми: без Next.js, серверных SDK и DOM. В `apps/web` перед кодом читать локальную документацию текущего Next.js и применимые AGENTS.md.
- Дата события — календарная дата; момент уведомления — дата + час + зона устройства. Повторная запись защищена идемпотентностью, многопозиционное сохранение атомарно.
- Данные примеров не переносить в пользовательские аккаунты. Непроверенный справочник доступен только в тестовом окружении до ветеринарной валидации.
- Не включать фото/файлы, серверные push, публичные ссылки, ежедневные напоминания о лекарствах, общий доступ и расписание для котят.
- Не менять проектную архитектуру авторизации, баланса и очереди анализа ради медкарты.
- Этапы не закрываются без `docs/verification/medical-record-NN.md`. Миграции и интеграционные тесты — на изолированной тестовой БД, не на production.

## На что направить ревью

1. Два сохранения и повтор запроса после обрыва сети: один результат, без двойных планов (MR-02/03).
2. Переход между питомцами и аккаунтами: ни сводка, ни уведомление не показывают чужое (MR-01/08/09).
3. Старые пустые поля: неизвестно не означает «здоров/не принимает»; миграция не выдумывает даты (MR-01/02/06).
4. Полночь, месяцы разной длины и смена часового пояса: сроки не прыгают на день (MR-03/05/08).
5. Удаление связанного визита/назначения: не теряются самостоятельно изменённые курсы (MR-07).

Эти случаи включены в нумерованные критерии соответствующих этапов.

## Проверенные точки входа репозитория

- `apps/mobile/app/(tabs)/pets/[id]/index.tsx` сейчас редактирует питомца; его поведение надо сохранить при переносе в `edit.tsx`.
- `apps/mobile/src/features/pets/PetFields.tsx`, `pet-form.ts` — существующая анкета.
- `apps/mobile/src/lib/api.ts`, `packages/shared/src/api-client.ts` — существующие сессия и API-клиент.
- `apps/web/src/app/(backend)/api/v1/pets/` — фактический корень серверных маршрутов питомцев.
- `apps/web/src/server/pets/pet-service.ts` — серверная логика анкеты.
- `packages/contracts/src/pet.ts`, `index.ts` — контракты и экспорты; новые сущности выделять в отдельный модуль.
- `apps/mobile/src/i18n/ru.ts`, `en.ts` — локализация; макеты русские, продукт сохраняет оба языка.
- `docs/architecture/deletion-data-map.md` — карта удаления, обновляется при каждой новой сущности.

Предлагаемые новые модули начинаются в `apps/mobile/src/features/medical-record/`, `apps/web/src/server/medical-record/` и `packages/shared/src/medical-record/`. Контракты и API-клиент расширяются только под текущий этап. Корни проверены при подготовке плана; исполнитель повторно проверяет их перед изменениями.

## Команды проверки

Из корня репозитория, после реализации выбранного этапа:

```sh
npm run typecheck --workspace=@lapka/contracts
npm run typecheck --workspace=@lapka/shared
npm run typecheck --workspace=@lapka/web
npm run typecheck --workspace=@lapka/mobile
npm run test --workspace=@lapka/shared
npm run test --workspace=@lapka/mobile -- src/features/medical-record
npm run test --workspace=@lapka/web -- tests/server/medical-record
```

Пути новых тестов создаются в текущем этапе; отсутствие тестов не считать успехом. Для интеграционных тестов сначала прочитать `apps/web/tests/support/db-guard.ts` и настройки test:integration; запускать адресный файл только с безопасной тестовой БД. После изменений существующего pet-service отдельно запустить существующие тесты анкеты и pet API. При добавлении native-модулей собрать development build и проверить реальное устройство; тест JavaScript этого не заменяет.

## Уточнения, которые этот план предлагает

Данные старой анкеты без даты остаются без выдуманной даты; завершённые курсы переживают удаление связанного визита; большой PDF переносится на дополнительные страницы вместо обрезки. Эти решения явно дополняют исходную спецификацию и проверяются при обсуждении соответствующего этапа. Открытые вопросы исходной спецификации — текст удаления питомца, проверка каталога ветеринаром и кнопка визита для healthy — не считаются автоматически согласованными.
