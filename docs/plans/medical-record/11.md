# MR-11. Общая приёмка и выпуск

> Для исполняющего агента: прочитать [общий план](README.md), исходную спецификацию и выполнить только этот этап через `superpowers:executing-plans`. Следующий этап не начинается автоматически.

**Цель:** Медкарта проверена как целый пользовательский путь и готова к отдельному решению о выпуске.

**Зависит от:** 01–10.

**Макеты:** Все 58 состояний; обязательные пути из handoff.

**Архитектура:** вертикальный этап: контракт → сервер/хранение → мобильный UI → проверки. Новые серверные маршруты входят в `/api/v1`; UI использует общий API-клиент.

**Стек:** текущие Expo/React Native, Next.js API, PostgreSQL, Zod, Vitest. Версии и инструкции проверяются в репозитории перед кодом.

## Файлы и границы

- `docs/architecture/deletion-data-map.md`

Новые пути — предлагаемая структура. Если эквивалент уже появился, расширить его и зафиксировать фактический путь, не создавать дубль. Для миграции `<новая_метка>` заменить на следующую свободную метку времени репозитория.

## Шаги

- [ ] Зафиксировать базовые проверки и убедиться, что зависимости этапа приняты, а не просто начаты.
- [ ] Создать тестовые сценарии по MR-11.1…4 ниже; для логики данных сначала воспроизвести отсутствие/ошибку поведения на минимальном тесте.
- [ ] На тестовой базе пройти миграции с нуля и обновление базы со старыми питомцами. Проверить возможность безопасного отключения новых возможностей без удаления данных.
- [ ] Пройти полное кольцо: создать питомца → вес → прививки → обработка → визит → лекарства → напоминание → сводка → проверка симптомов.
- [ ] Проверить RLS реальными запросами от двух владельцев, повтор запроса, удаление питомца и аккаунта, отсутствие следов в списках/сводках/очереди уведомлений.
- [ ] Проверить 390×844, 360×640, 200% шрифт, VoiceOver/TalkBack, клавиатуру, длинные названия, офлайн и возврат после перезапуска.
- [ ] Сверить все строки RU/EN с существующей системой i18n, хотя артборды русские. Не менять юридический смысл сводки и клинические действия проверки.
- [ ] Записать номера сборок, устройства, тесты, результаты и оставшиеся ограничения. Не закрывать этап без отчёта и не выпускать непроверенный ветеринаром справочник.
- [ ] Запустить адресные тесты, проверки типов и регрессию затронутых старых сценариев. Проверки SQL-транзакций/RLS выполнить на изолированной тестовой базе, не ограничиваться моками.
- [ ] Сверить UI с указанными артбордами; записать доказательства для каждого критерия в `docs/verification/medical-record-11.md`. Отдельно записать то, что проверить не удалось.
- [ ] Представить рабочий результат этапа на приёмку. Незакрытые критерии означают, что этап не завершён.

## Нумерованные критерии приёмки

- [ ] **MR-11.1** Все критерии MR-01…MR-10 имеют ссылку на доказательство в отчётах.
- [ ] **MR-11.2** Старые анкеты, анализ, история, баланс и удаление аккаунта проходят регрессию.
- [ ] **MR-11.3** Нет активных блокирующих дефектов приватности, потери данных и непроверенных продуктов в справочнике.
- [ ] **MR-11.4** Публикация/деплой не выполняются автоматически по факту готовности плана.

## Тесты этого этапа

Предлагаемые новые файлы: `apps/web/tests/server/medical-record/stage-11.test.ts`, `apps/web/tests/integration/medical-record-11.test.ts`, `apps/mobile/src/features/medical-record/stage-11.test.ts`. Создавать только относящиеся к этапу; чистый UI не требует фиктивного серверного теста. Нативные сценарии фиксируются отдельно с устройством/версией ОС.

Команды запуска и шаблон отчёта — в общем плане. Для MR-11 ожидается успешное выполнение каждого критерия выше, а не только зелёный общий набор тестов.
