# MR-05. Обработки от паразитов

> Для исполняющего агента: прочитать [общий план](README.md), исходную спецификацию и выполнить только этот этап через `superpowers:executing-plans`. Следующий этап не начинается автоматически.

**Цель:** Можно вести обработки и планы отдельно по блохам, клещам и глистам.

**Зависит от:** 03, 04.

**Макеты:** М8, М16, X-complete, X-catalog-parasites, X-parasites-empty.

**Архитектура:** вертикальный этап: контракт → сервер/хранение → мобильный UI → проверки. Новые серверные маршруты входят в `/api/v1`; UI использует общий API-клиент.

**Стек:** текущие Expo/React Native, Next.js API, PostgreSQL, Zod, Vitest. Версии и инструкции проверяются в репозитории перед кодом.

## Файлы и границы

- `apps/mobile/src/features/medical-record/ParasitesScreen.tsx (новый)`
- `apps/mobile/src/features/medical-record/EventForm.tsx`
- `apps/web/src/server/medical-record/event-service.ts`
- `apps/web/src/server/medical-record/catalog-service.ts`

Новые пути — предлагаемая структура. Если эквивалент уже появился, расширить его и зафиксировать фактический путь, не создавать дубль. Для миграции `<новая_метка>` заменить на следующую свободную метку времени репозитория.

## Шаги

- [ ] Зафиксировать базовые проверки и убедиться, что зависимости этапа приняты, а не просто начаты.
- [ ] Создать тестовые сценарии по MR-05.1…4 ниже; для логики данных сначала воспроизвести отсутствие/ошибку поведения на минимальном тесте.
- [ ] Расширить общий тип события обработкой, не создавать параллельную систему дат и повторов.
- [ ] Добавить справочник средств по виду; цели интерфейса сворачивать в Блохи/Клещи/Глисты, сохраняя точные цели справочника в данных.
- [ ] Собрать две статусные карточки, список сделанного/планов и форму с несколькими позициями; на 360 px карточки вертикальные.
- [ ] Сводный комбинированный препарат показывать в обеих подходящих карточках, но не создавать дублирующий план для одного item_id.
- [ ] Подключить общие перенос, завершение одной позиции, отмену и общий список сроков. Показывать расчёт следующей даты и право владельца изменить её.
- [ ] Запустить адресные тесты, проверки типов и регрессию затронутых старых сценариев. Проверки SQL-транзакций/RLS выполнить на изолированной тестовой базе, не ограничиваться моками.
- [ ] Сверить UI с указанными артбордами; записать доказательства для каждого критерия в `docs/verification/medical-record-05.md`. Отдельно записать то, что проверить не удалось.
- [ ] Представить рабочий результат этапа на приёмку. Незакрытые критерии означают, что этап не завершён.

## Нумерованные критерии приёмки

- [ ] **MR-05.1** Бравекто 12 недель от 24.09.2026 → 17.12.2026; 3 месяца → 24.12.2026.
- [ ] **MR-05.2** Два средства с разными интервалами сохраняют разные планы.
- [ ] **MR-05.3** Комбинированное средство видно в двух группах, но в хранилище и уведомлении нет дубля позиции.
- [ ] **MR-05.4** Срок обработки не окрашен как срочность проверки; защищённый вид препарата контролируется сервером.

## Тесты этого этапа

Предлагаемые новые файлы: `apps/web/tests/server/medical-record/stage-05.test.ts`, `apps/web/tests/integration/medical-record-05.test.ts`, `apps/mobile/src/features/medical-record/stage-05.test.ts`. Создавать только относящиеся к этапу; чистый UI не требует фиктивного серверного теста. Нативные сценарии фиксируются отдельно с устройством/версией ОС.

Команды запуска и шаблон отчёта — в общем плане. Для MR-05 ожидается успешное выполнение каждого критерия выше, а не только зелёный общий набор тестов.
